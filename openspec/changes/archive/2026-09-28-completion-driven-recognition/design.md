## Context

Профиль показал 108 с ожидания ранних результатов при наличии готовых поздних.
Диагностический эксперимент увеличил среднюю загрузку машины с 35% до 92%.
Его максимальный буфер готовых наблюдений составил 473 на 24 процесса.
Пользователь также запросил скорость обработки, обновляемую при смене процента.

## Goals / Non-Goals

Устранить блокировку подачи порядком выдачи при ограниченном расходе памяти.
Сохранить исходный порядок наблюдений, OCR-расписание и полный игровой JSON.

## Decisions

- pending хранит Future → порядковый номер. wait(FIRST_COMPLETED) собирает
  готовые задания; ready хранит номер → Observation без исходных изображений.
- Сначала выдаются доступные результаты по порядку, затем пополняется pending
  до 2*N при общем окне submitted-emitted < 32*N. При заполнении окна ждём
  оставшиеся задания; завершение раннего гарантирует продвижение окна.
- Окно 32*N ограничивает память независимо от длины видео и вмещает измеренный
  максимум 473 наблюдения при N=24 (предел 768). Только pending держит изображения.
- Ошибка любого завершившегося Future прекращает источник; finally отменяет
  ожидающие задания и закрывает executor и генератор кадров.
- ConsoleProgress.update получает processed_seconds от менеджера. Хранит последнее
  обработанное время и скорость; пересчитывает скорость только при смене целого
  процента. Таймер форматирует сохранённую скорость, не пересчитывая её.
- В конце чтения менеджер передаёт полную длительность в update(99); при finish(True)
  процент становится 100 и скорость пересчитывается с итоговым временем.
- Делитель — монотонное время без усечения, при нуле скорость 0; формат .2f с
  удалением конечных нулей. Последовательный режим использует тот же расчёт.

## Risks / Trade-offs

Очень медленный первый кадр → при достижении предела окна допускается простой,
но не рост памяти с длиной видео. Постоянная загрузка CPU 100% не гарантируется.
Скорость между изменениями процента намеренно заморожена согласно запросу.

## Migration Plan

Падающие тесты, реализация, полный набор проверок, повторный прогон образца,
обновление README и архивирование. Новые зависимости и аргументы не нужны.

## Проверка реализации

154 теста прошли (35,95 с), Ruff и проверка форматирования пройдены.
Проверены пополнение очереди за медленным ранним кадром, лимиты 2*N и 32*N,
порядок/OCR-расписание, ошибка позднего кадра до завершения раннего, отмена,
настоящие spawn-процессы и отсутствие оставшихся процессов после сбоя.
Проверена заморозка скорости между изменениями процента, нулевое время,
сброс для следующего файла и формат до двух знаков без конечных нулей.

Продуктовая очередь на образце: 103,49 с, средняя загрузка всей машины 91,9%.
До изменения: 134,73 с и 34,6%. Учтённая загрузка приложения — около 84% от
24 логических CPU; показатель всей машины включает фоновые процессы.
1126 наблюдений, полный игровой JSON совпал с tests/fixtures/sample_game.json.
SHA-256 исходного видео до/после совпал.
Итоговая строка: Обработано 100% за 103 сек скорость 2.81x.
Это один диагностический прогон каждого режима, не гарантия на другом компьютере.
Измерения сохранены в .analysis/cpu-profile/production-bounded; в приложение
профилирующий инструментарий не добавлялся.
