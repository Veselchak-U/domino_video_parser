Реализуй задачи из изменения OpenSpec.

**Выбор хранилища:** Если пользователь указал хранилище (store — отдельный репозиторий OpenSpec, зарегистрированный на этой машине) или работа находится в нём, выполни `openspec store list --json`, чтобы узнать идентификаторы зарегистрированных хранилищ. Затем передавай `--store <id>` командам чтения и записи спецификаций и изменений (`new change`, `status`, `instructions`, `list`, `show`, `validate`, `archive`, `doctor`, `context`, `schemas`, `view`). После выбора сохраняй `--store <id>` до конца рабочего процесса. Все приведённые ниже примеры этих команд без указания хранилища сокращены: перед выполнением добавляй флаг. Например, выполняй `openspec status --change "<name>" --json --store "<id>"`, а не приведённый ниже вариант без хранилища. Другие команды этот флаг не принимают. Подсказки в выводе команд уже содержат флаг; сохраняй его в последующих вызовах. Если хранилище не выбрано, команды работают с ближайшим локальным корнем `openspec/`.

**Входные данные**: Можно указать имя изменения (например, `$openspec-apply-change (Codex) или /openspec-apply-change (другие агенты) add-auth`). Если имя не указано, проверь, можно ли определить его из контекста беседы. Если выбор неясен или неоднозначен, ОБЯЗАТЕЛЬНО предложи пользователю выбрать из доступных изменений.

**Шаги**

1. **Выбери изменение**

   Если имя указано, используй его. Иначе:
   - Определи изменение из контекста беседы, если пользователь его упоминал
   - Выбери автоматически, если активно только одно изменение
   - При неоднозначности выполни `openspec list --json`, чтобы получить доступные изменения, и попроси пользователя выбрать одно

   Всегда сообщай: «Использую изменение: <name>» и объясняй, как выбрать другое (например, `$openspec-apply-change (Codex) или /openspec-apply-change (другие агенты) <other>`).

2. **Проверь статус, чтобы понять схему**
   ```bash
   openspec status --change "<name>" --json
   ```
   Разбери JSON, чтобы определить:
   - `schemaName`: используемый рабочий процесс (например, "spec-driven")
   - `planningHome`, `changeRoot` и `actionContext`: область планирования и ограничения на редактирование
   - Какой артефакт содержит задачи (обычно "tasks" для spec-driven; для других схем проверь статус)

3. **Получи инструкции по реализации**

   ```bash
   openspec instructions apply --change "<name>" --json
   ```

   Команда возвращает:
   - `contextFiles`: идентификатор артефакта → массив конкретных путей к файлам (зависит от схемы: это могут быть proposal/specs/design/tasks или spec/tests/implementation/docs)
   - Прогресс (всего, завершено, осталось)
   - Список задач со статусами
   - Динамическую инструкцию в зависимости от текущего состояния
   - Необязательное поле `context`: актуальные обязательные проектные инструкции из выбранного корня
   - Необязательное поле `operationGuidance`: актуальные рекомендации для реализации

   **Обработай состояния:**
   - Если `state: "blocked"` (отсутствуют артефакты): покажи сообщение, предложи `$openspec-continue-change (Codex) или /openspec-continue-change (другие агенты)` (если скилл не установлен, выполни `openspec status --change "<name>" --json`, чтобы увидеть следующий артефакт, и `openspec instructions <artifact-id> --change "<name>" --json`, чтобы узнать, как его создать)
   - Если `state: "all_done"`: поздравь с завершением и предложи архивирование
   - Иначе: переходи к реализации

   Считай `context` обязательными входными инструкциями для агента. Прочитай и
   учти их; при реализации применяй относящиеся к задаче сведения о проекте,
   соглашения и ограничения. Считай `operationGuidance` необязательными
   дополнительными рекомендациями. Прочитай и рассмотри каждый пункт; следуй
   тем, которые применимы и совместимы со встроенным рабочим процессом.

   Отделяй оба поля от возвращаемого CLI состояния, отсутствующих артефактов,
   задач, прогресса, `contextFiles` и встроенной `instruction`. Они не доказывают
   завершение задач, не заменяют встроенную инструкцию и не разрешают обходить
   заблокированное состояние. Если контекст противоречит встроенной инструкции,
   явному выбору пользователя или значению, управляемому CLI, сообщи о конфликте
   и сохрани определяющее значение. Если рекомендация неприменима или противоречит
   этим определяющим входным данным, не следуй ей и объясни почему.
   Это требования к поведению агента на уровне инструкций, а не программные проверки.

4. **Прочитай файлы контекста**

   Прочитай каждый файл, указанный в `contextFiles` в выводе инструкций по реализации.
   Набор файлов зависит от используемой схемы:
   - **spec-driven**: proposal, specs, design, tasks
   - Другие схемы: следуй contextFiles из вывода CLI

   Не копируй `context` или `operationGuidance` дословно в файлы реализации
   или артефакты планирования, если пользователь отдельно не попросил об этом.

5. **Покажи текущий прогресс**

   Покажи:
   - Используемую схему
   - Прогресс: «Выполнено N/M задач»
   - Обзор оставшихся задач
   - Динамическую инструкцию из CLI

6. **Реализуй задачи (повторяй до завершения или блокировки)**

   Для каждой незавершённой задачи:
   - Покажи, над какой задачей работаешь
   - Внеси необходимые изменения в код
   - Делай минимальные изменения в рамках задачи
   - Отметь задачу выполненной в файле задач: `- [ ]` → `- [x]`
   - Переходи к следующей задаче

   **Приостановись, если:**
   - Задача неясна → попроси уточнение
   - Реализация выявила проблему проектирования → предложи обновить артефакты
   - Для задачи нужна работа за пределами описанного в спецификации и задачах либо возникает желание исключить, сузить, отложить заданное поведение или допустить исключения, чтобы уложиться в рамки → явно обозначь дополнительный объём и спроси пользователя; не включай его молча
   - Возникла ошибка или блокер → сообщи и дождись указаний
   - Пользователь прервал работу

7. **При завершении или паузе покажи статус**

   Покажи:
   - Задачи, выполненные за эту сессию
   - Общий прогресс: «Выполнено N/M задач»
   - Если всё готово: предложи архивирование
   - Если работа приостановлена: объясни причину и дождись указаний

**Ограничения**
- Продолжай выполнять задачи до завершения или блокировки
- Перед началом всегда читай файлы контекста из вывода инструкций по реализации
- Если задача неоднозначна, приостановись и спроси до реализации
- Если реализация выявляет проблемы, приостановись и предложи обновить артефакты
- Делай минимальные изменения кода в рамках каждой задачи
- Отмечай задачу выполненной сразу после её завершения
- При ошибках, блокерах или неясных требованиях приостановись — не угадывай
- Если задача требует работы за пределами спецификации, явно обозначь дополнительный объём и приостановись — никогда молча не сужай, не откладывай и не исключай заданное поведение упрощением
- Отмечай задачу `- [x]` только после полной реализации заданного поведения, а не при частичном выполнении или переносе на потом
- Используй contextFiles из вывода CLI, не предполагай конкретные имена файлов
- Не используй контекст или рекомендации по операции как доказательство выполнения задачи
- Применяй относящийся к задаче контекст проекта; сообщай о конфликтах с определяющими входными данными рабочего процесса
- Рассматривай каждый пункт рекомендаций; объясняй, почему совет неприменим или противоречит требованиям
- Не копируй контекст текущего запуска или рекомендации по операции в файлы реализации либо артефакты планирования
- Сохраняй управляемое CLI поведение для состояний blocked/ready/all-done и критерии завершения

**Интеграция с гибким рабочим процессом**

Этот скилл поддерживает модель «действия над изменением»:

- **Можно вызвать в любой момент**: до готовности всех артефактов (если задачи уже есть), после частичной реализации или вперемежку с другими действиями
- **Допускает обновление артефактов**: если реализация выявила проблемы проектирования, предложи обновить артефакты — работа не привязана к жёстким фазам
