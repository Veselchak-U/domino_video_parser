## Context

Мотивация и состав компонентов — в [proposal.md](proposal.md). Действующих спецификаций или приложения в рабочем каталоге нет. Предоставленный MP4 имеет размер 72 298 495 байт, кадр 720×1608 и длительность 290.472104 секунды. Изображение игрового стола становится горизонтальным после поворота на 90 градусов против часовой стрелки. По выборочным кадрам видны три кона, раскрытие остатков около 85, 190 и 275–280 секунд, финальный экран около 290 секунд. Табло показывает лимит 50; финальные 96:29 и начисления обеим командам после последней рыбы согласуются с withoutEggs. Это предварительные наблюдения, не готовый эталон раздач и ходов.

Проверенный внешний контракт требует все начальные руки, хотя они скрыты во время игры. Раскрытые остатки позволяют восстановить руки ретроспективно. Исходный видеоряд и точная ручная разметка станут интеграционным тестом после согласования; пока проверены только выборочные кадры.

## Goals / Non-Goals

**Goals:** простой воспроизводимый запуск на Windows, полностью локальное распознавание заданного интерфейса, отделённая проверка правил и пригодная для исправления диагностика.

**Non-Goals:** универсальное распознавание любого домино, угадывание закрытых рук, адаптация правил под ошибочно распознанные данные. Полный объём и исключения заданы proposal.

## Decisions

1. **Python 3.11+, argparse, PyAV, OpenCV, RapidOCR/ONNX Runtime, jsonschema, pytest.** Python имеет подходящие библиотеки обработки кадров; PyAV не требует отдельного ffmpeg в PATH, локальный OCR не требует ключей API. Flutter добавил бы интерфейс без пользы для обработки файлов. Облачная мультимодальная модель не выбрана из-за стоимости и недетерминированности. Конкретные совместимые версии фиксируются после проверки установки. Модели OCR включаются в установку либо загружаются отдельной документированной командой; анализ видео не запускает скрытую загрузку.

2. **Нормализация кадра и профиль интерфейса.** Определить ориентацию по расположению стола и панелей, привести координаты к горизонтальному эталону. Выделять светлые прямоугольники, половины и точки; различать дубль, поворот, затенение руки и подсветку. OCR запускать только для областей имён, счёта и итогов, повторять на соседних кадрах. Имена `You`/профиль на финальном экране связывать по месту; неоднозначность не разрешать молча. Начальные места назначаются по часовой стрелке от нижнего игрока; соответствие фактическому порядку проверяется по анимациям и индикатору активного игрока.

3. **Сначала наблюдения, затем журнал.** Потоковая обработка кадров не загружает видео целиком. Базовые кадры дополняются плотным разбором интервалов изменения; переходы между устойчивыми состояниями отслеживаются, а промежуточная анимация не считается ходом. Учитывать перемещение и уменьшение всей цепочки, устанавливать идентичность камня по значениям и соседям. Игрок хода определяется анимацией, изменением счётчика и очередью. Непрерывность без объяснимого перехода становится проблемой, а не пропуском события. Частота выборки и пороги — внутренние параметры, подбираемые на разметке, без обещания универсальной точности.

4. **Реконструкция с ограничениями.** Выкладки и раскрытые остатки образуют руки. Уточнять кандидатов через полный набор, размер руки, очередь и обязательные пасы. Экспортировать только единственное подтверждённое решение; ограничить поиск кандидатов и диагностировать превышение, не зависать. Не выводить начальные руки только из итоговой суммы очков. Смена игроков/обнуление счёта и экран результатов задают границы партий, очистка стола сама по себе — лишь возможную границу кона.

5. **Независимое воспроизведение.** Валидатор реализует контракт R1–R12/V1–V4: заход 1-1 до первой записи, далее вышедший/рыбак; рыбак — последний недубль; выход приоритетнее рыбы; стоимость одиночного 0-0 равна 10; порог открытия 13 применяется только к собственному остатку. Начисления проверяются по таблицам внешних правил, включая яйца, забор, оба лимита и ничью. Сериализатор сохраняет компактный журнал без добавления таймкодов и confidence внутрь kozel-game-v1. Все технические данные идут в отчёт.

6. **CLI и восстановление после ошибок.** Планируемый вызов:

   ```text
   domino-video video1.mp4 video2.mp4 --output out --fish-variant withoutEggs --score-limit 50
   ```

   Необязательный `--corrections corrections.json` принимает документ с массивом источников по SHA-256. Для каждого источника: переопределение состава по местам и исправления по партии/кону; для рук — полная рука, для событий — замена/вставка/удаление с явным индексом исходного события. Все индексы относятся к исходному отчёту, применяются одним пакетом, конфликтующие операции отклоняются. Отчёт содержит этот шаблон и привязку к исходному видео. Существующие файлы не заменяются: повторный запуск использует другой/очищенный пользователем каталог.

7. **Установка и проверка вместо старых Flutter-команд.** При реализации добавить pyproject.toml, русское README и обновить устаревшее описание стека в AGENTS.md. Применимые общие требования к архитектуре и TDD сохранить. Тесты Python в tests/, запуск pytest; отсутствующие Flutter-код и tools/tests/run_unit_tests.sh не представлять существующими проверками. Это следствие явно разрешённого пользователем выбора стека.

## Risks / Trade-offs

- Камни скрыты или раскрытие обрезано → диагностический отчёт и исправления; нельзя гарантировать экспорт произвольной записи.
- Законная реконструкция не доказывает визуальную точность → ручной эталон всех событий предоставленной записи и проверка изменений счёта, тесты поворота/масштаба/пропусков.
- Возможные отличия правил мобильной игры → явный конфликт со спецификацией; не менять правила под видео. По выборочным кадрам противоречий не установлено, полная проверка ещё предстоит.
- Низкая точность OCR имён → несколько кадров и исправление имён с сохранением мест; имена не заменять выдуманными.
- Несколько последовательностей удовлетворяют правилам → отчёт вместо произвольного выбора.
- Только один предоставленный образец → поддержка ограничена данным визуальным профилем; проценты точности на других видео не заявляются.

## Migration Plan

Создать Python-пакет после явного согласования change. Зафиксировать копию внешних правил/схемы/примера с хешами для автономной проверки; соседний репозиторий не менять. Исследовательские .analysis и .analysis-deps не являются зависимостями приложения, исключить их из публикуемого проекта. Проверить чистую установку, CLI и эталонное видео. Откат — удаление только созданного пакета; пользовательские видео и результаты сохраняются.

## ADR: уточнения после проверки кадров

Декодер использует временные метки PTS и выдаёт до четырёх кадров в секунду; сами кадры не накапливаются. Между кадрами сохраняются только компактные наблюдения. Камень принимается после трёх устойчивых наблюдений; положение уже известного камня помогает отбрасывать ошибочное чтение закрытых точек. Авторство уточняется ограниченным перебором кандидатов по таймеру, видимой начальной руке и запретам, вытекающим из пасов. Предел поиска — 4096 состояний внутри кона и 128 сочетаний конов; превышение является диагностикой.

Для финальной выкладки интерфейс иногда убирает стол до появления трёх устойчивых кадров. Допускается только восстановление единственного недостающего камня, когда остальные 27 известны, исполнитель наблюдался, а полное воспроизведение даёт единственный законный результат. Это реализация предусмотренного восстановления с ограничениями, не подстановка эталона.

Имена и счёт читаются каждые пять секунд; когда стол очищен, счёт читается на каждом выбранном кадре. Это необходимо для короткого промежутка между завершением анимации начислений и экраном результата. Вычисленный результат по-прежнему обязан совпадать с наблюдаемым. На исходной записи ручная разметка содержит 26, 27 и 19 действий по конам; итог 96:29.

Внешний контракт и область поддержки не изменились. OCR-счётчики числа камней включаются в технические наблюдения, но не подменяют проверку восстановленных рук.
