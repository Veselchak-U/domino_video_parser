## Context

См. [proposal.md](proposal.md). Порог из `ocr_result.py` импортируется в NameReading/NameOCR, PlayerNameResolver, PreparedObservation и RecognitionDiagnostics. Простая замена общего значения на 0.7 снизила бы также порог счёта и счётчиков.

## Goals / Non-Goals

**Goals:** отдельный единый порог для всех решений о символах имени, сохранение порога числовых полей.

**Non-Goals:** CLI-настройка порогов, новые модели и изменение алгоритма камней.

## Decisions

Сохранить `OCR_THRESHOLD = 0.8`; рядом определить `NAME_OCR_THRESHOLD = 0.7`. NameReading/NameOCR и PlayerNameResolver используют только порог имени. PreparedObservation выбирает значение метаданных по типу поля; отсутствующая попытка имени в resolver также записывает 0.7. RecognitionDiagnostics продолжает использовать 0.8 для отсутствующей попытки счёта. Общая константа без разделения отвергнута, поскольку пользователь ограничил изменение именами.

Сохранить строгое сравнение `>`: точное 0.7 не принимается. Тесты имён, ранее проверявшие границу 0.8, перевести на новую границу; отдельные проверки счёта и счётчиков оставить на 0.8. Архивы завершённых изменений не переписывать. README описывает оба порога.

## Risks / Trade-offs

Больше принятых символов может означать больше неверных символов → сохраняются исходные вероятности, маски при уверенности ≤0.7, ручные исправления и контроль настоящего участка видео. Улучшение точности заранее не заявляется.

## Migration Plan

После согласования: падающие проверки граничных значений и раздельных полей, затем отделение констант и документация. Проверить CPU/GPU IPC, полный pytest, Ruff и OpenSpec. Откат возвращает только порог имени к 0.8; ранее экспортированные Unicode-имена остаются валидными.

## Проверка реализации

Вероятность проблемного символа `ј` около 0.694, ниже обоих порогов. Сравнение выполнено без сети; SHA-256 исходного файла остался `42ff9fd0e8a584acbca4cc22e40d6de9b1a6b2a82bd6df2745c39f680f6f998e`. Улучшение написания на этом участке не наблюдалось. Модели и алгоритм камней не менялись.
