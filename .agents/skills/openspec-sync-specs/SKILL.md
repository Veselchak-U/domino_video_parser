Синхронизируй дельта-спецификации изменения с основными спецификациями.

Эту операцию **выполняет агент**: ты читаешь дельта-спецификации и напрямую
редактируешь основные спецификации, применяя изменения. Это позволяет выполнять
интеллектуальное слияние, например добавлять сценарий без копирования требования целиком.

**Выбор хранилища:** Если пользователь указал хранилище (store — отдельный репозиторий OpenSpec, зарегистрированный на этой машине) или работа находится в нём, выполни `openspec store list --json`, чтобы узнать идентификаторы зарегистрированных хранилищ. Затем передавай `--store <id>` командам чтения и записи спецификаций и изменений (`new change`, `status`, `instructions`, `list`, `show`, `validate`, `archive`, `doctor`, `context`, `schemas`, `view`). После выбора сохраняй `--store <id>` до конца рабочего процесса. Все приведённые ниже примеры этих команд без указания хранилища сокращены: перед выполнением добавляй флаг. Например, выполняй `openspec status --change "<name>" --json --store "<id>"`, а не приведённый ниже вариант без хранилища. Другие команды этот флаг не принимают. Подсказки в выводе команд уже содержат флаг; сохраняй его в последующих вызовах. Если хранилище не выбрано, команды работают с ближайшим локальным корнем `openspec/`.

`<capability-path>` — каталог спецификации относительно `specs/` (например, `user-auth` или `identity/user-auth`). При определении основной спецификации сохраняй полный путь из каждой дельта-спецификации.

**Входные данные**: Можно указать имя изменения. Если имя не указано, проверь, можно ли определить его из контекста беседы. Если выбор неясен или неоднозначен, ОБЯЗАТЕЛЬНО предложи пользователю выбрать из доступных изменений.

**Шаги**

1. **Выбери изменение**

   Если имя указано, используй его. Иначе:
   - Определи изменение из контекста беседы, если пользователь его упоминал
   - Выбери автоматически, если активно только одно изменение
   - При неоднозначности выполни `openspec list --json`, чтобы получить доступные изменения, и попроси пользователя выбрать одно

   При выборе показывай изменения с дельта-спецификациями в каталоге `specs/`.

   Всегда сообщай: «Использую изменение: <name>» и объясняй, как выбрать другое (например, `$openspec-sync-specs (Codex) или /openspec-sync-specs (другие агенты) <other>`).

2. **Определи контекст изменения**

   Выполни:
   ```bash
   openspec status --change "<name>" --json
   ```

   JSON содержит `planningHome.root`. Основные спецификации находятся в
   `<planningHome.root>/openspec/specs/` — используй этот учитывающий хранилище
   корень для всех путей основных спецификаций ниже, а не жёстко заданный путь
   репозитория. При выборе хранилища он указывает на хранилище, а не на текущий репозиторий.

3. **Найди дельта-спецификации**

   Единственный источник путей дельта-спецификаций —
   `artifactPaths.specs.existingOutputPaths` из JSON статуса. Если запись
   `specs` отсутствует или `existingOutputPaths` пуст, сообщи, что дельта-спецификаций
   для синхронизации нет; не определяй их по другим артефактам и остановись,
   не запрашивая инструкции артефактов и не записывая основную спецификацию.

   Синхронизируй каждый путь из `existingOutputPaths`, если вызывающая сторона
   не сузила набор. Для сужения она указывает явный список полных записей из
   `existingOutputPaths` — копируй эти абсолютные значения дословно.
   Архивирование делает это внутри своего процесса; пользователь тоже может
   выбрать запись, например оканчивающуюся на `/specs/billing/invoices/spec.md`.
   Тогда синхронизируй только указанные пути, не трогая остальные дельта-спецификации:
   массовое архивирование исключает дельту, реализацию которой не удалось найти,
   и её синхронизация всё равно записала бы основную спецификацию, которую
   вызывающая сторона намеренно исключила. Сохраняй суженный набор в шаге 4;
   никогда не расширяй его обратно до полного списка. Если указанного пути нет
   в `existingOutputPaths`, не синхронизируй его: сообщи об этом и остановись,
   а не отбрасывай путь молча. Если переданный список пуст, сообщи, что
   синхронизировать нечего, и остановись без записи основной спецификации.

   Каждый файл дельта-спецификации содержит разделы вида:
   - `## ADDED Requirements` — новые требования для добавления
   - `## MODIFIED Requirements` — изменения существующих требований
   - `## REMOVED Requirements` — требования для удаления
   - `## RENAMED Requirements` — требования для переименования (формат FROM:/TO:)

   Если дельта-спецификации не найдены, сообщи пользователю и остановись.

4. **Для каждой дельта-спецификации примени изменения к основным спецификациям**

   До первой записи основной спецификации получи один актуальный снимок правил specs:
   - Если архивирование вызвало этот процесс внутри своей работы и передало валидный снимок из `openspec instructions specs --change "<name>" --json`, используй его повторно и не запрашивай те же инструкции снова.
   - Иначе выполни эту команду один раз сейчас с теми же флагами выбранного корня.
   - Если прямой запрос завершился с ненулевым кодом или вернул невалидный JSON инструкций артефакта, сообщи об ошибке и остановись до записи любой основной спецификации. Не считай сбой отсутствием правил.
   - Валидный ответ без `rules` означает, что правила артефакта не настроены; существующее семантическое слияние продолжается.

   Применяй полученные `rules` только к содержанию и форме основных спецификаций,
   создаваемых этим слиянием. Правила артефактов не являются рекомендациями по
   операции и не могут менять выбранные корни, пути дельт, проверки CLI или шаги
   рабочего процесса. Используй их текст как ограничения, не копируя дословно
   в основную спецификацию или сводку.

   Для каждого пути дельта-спецификации возможности, выбранного в шаге 3, —
   полного списка `existingOutputPaths` или суженного подмножества, если его
   передала вызывающая сторона (пути могут относиться к выбранному хранилищу,
   а не к репозиторию):

   a. **Прочитай дельта-спецификацию**, чтобы понять задуманные изменения

   b. **Прочитай основную спецификацию** по пути `<planningHome.root>/openspec/specs/<capability-path>/spec.md` (она может ещё не существовать)

   c. **Примени изменения с учётом смысла**:

      **ADDED Requirements:**
      - Если требования нет в основной спецификации → добавь его
      - Если требование уже есть → обнови до соответствия дельте (считай неявным MODIFIED)

      **MODIFIED Requirements:**
      - Найди требование в основной спецификации
      - Примени изменения; это могут быть:
        - Добавление новых сценариев, которых ещё нет в основной спецификации
        - Правка существующих сценариев
        - Изменение описания требования
      - Сохраняй сценарии и содержимое, не упомянутые в дельте

      **REMOVED Requirements:**
      - Удали весь блок требования из основной спецификации
      - Вывод возможности из использования. Удаляй весь `spec.md`, а затем его каталог, если в нём ничего не осталось, только при выполнении ВСЕХ условий:
        1. удаление требований *в этом запуске* не оставило ни одного блока требования;
        2. остальная спецификация корректно оформлена (в ней всё ещё есть `## Purpose`);
        3. основная спецификация не была пустой до синхронизации: если ничего не удалял, ничего не меняй;
        4. каждая другая непустая строка во всём файле относится к заголовку документа, Purpose, заголовку Requirements либо тексту, сценариям или примерам в блоках кода канонического требования;
        5. в `.openspec.yaml` изменения объявлено `retire_capabilities: true`;
        6. разрешённый путь `spec.md` находится внутри фактического корня specs (не следуй по символической ссылке каталога возможности для удаления внешнего файла).
        Если удаление выбранных требований не оставит блоков требований и хотя бы
        одно условие вывода из использования не выполнено, не меняй основную
        спецификацию. Останови синхронизацию этой возможности, сообщи о блокирующем
        условии и объясни пользователю, как его устранить. Никогда не записывай
        и не оставляй пустой раздел `## Requirements`. Если отсутствует только
        маркер, также скажи об этом: пользователь может добавить именно его,
        чтобы разрешить вывод возможности из использования.
      - Удаление файла удаляет и его `## Purpose`; любой другой раздел блокирует вывод из использования. Упоминай Purpose в отчёте о таком удалении. Давай готовую для копирования команду `git checkout` только если спецификация находилась в рабочей копии вызывающей стороны; иначе дай инструкции восстановления с явным указанием нужной рабочей копии.

      **RENAMED Requirements:**
      - Найди требование FROM и переименуй в TO

      **`## Purpose` в дельте:**
      - В основной спецификации он уже есть и является определяющим — не меняй его (так работает `openspec archive`: предупреждает и продолжает)

   d. **Создай новую основную спецификацию**, если возможности ещё нет:
      - Создай `<planningHome.root>/openspec/specs/<capability-path>/spec.md`
      - Добавь раздел Purpose: дословно скопируй содержимое `## Purpose` из дельты, если оно есть (так работает `openspec archive`); только при его отсутствии запиши краткую заглушку TBD
      - Добавь раздел Requirements с требованиями ADDED
      - Следуй **справочнику формата основной спецификации** ниже

5. **Проверь обновлённые основные спецификации**

   Выполни `openspec validate --specs` с теми же флагами выбранного корня.
   Если проверка не прошла, сообщи о проблемах и не утверждай, что синхронизация успешна.

6. **Покажи сводку**

   После применения всех изменений укажи:
   - Какие возможности обновлены
   - Какие изменения внесены (требования добавлены, изменены, удалены, переименованы)
   - Все новые основные спецификации, оставленные с заглушкой TBD в Purpose, чтобы заполнить её сейчас, а не оставлять надолго
   - Все выведенные из использования возможности: назови удалённый `spec.md`, его Purpose и дай готовую команду `git checkout` либо инструкции восстановления с указанием рабочей копии

**Справочник формата дельта-спецификации**

```markdown
## Purpose

Только для дельты, вводящей совершенно новую возможность. Задаёт содержимое новой основной спецификации.

## ADDED Requirements

### Requirement: Новая функция
Система SHALL выполнять новое действие.

#### Scenario: Базовый случай
- **WHEN** пользователь делает X
- **THEN** система делает Y

## MODIFIED Requirements

### Requirement: Существующая функция
Система SHALL продолжать выполнять существующее действие, теперь также обрабатывая A.

#### Scenario: Сценарий, который уже есть в основной спецификации
- **WHEN** пользователь делает X
- **THEN** система делает Y

#### Scenario: Новый сценарий для добавления
- **WHEN** пользователь делает A
- **THEN** система делает B

## REMOVED Requirements

### Requirement: Устаревшая функция

## RENAMED Requirements

- FROM: `### Requirement: Старое имя`
- TO: `### Requirement: Новое имя`
```

**Справочник формата основной спецификации**

Основные спецификации — это то, ВО ЧТО вливается дельта. Они никогда не должны
содержать заголовки операций дельты (`## ADDED/MODIFIED/REMOVED/RENAMED Requirements`):
после синхронизации каждое требование находится в едином разделе `## Requirements`:

```markdown
# <capability> Specification

## Purpose
Краткое описание того, что делает эта возможность и зачем она существует.

## Requirements

### Requirement: Новая функция
Система SHALL выполнять новое действие.

#### Scenario: Базовый случай
- **WHEN** пользователь делает X
- **THEN** система делает Y
```

**Ключевой принцип: интеллектуальное слияние**

В отличие от программного слияния, ты объединяешь содержимое, а не перезаписываешь:
- Блок MODIFIED содержит требование целиком: текст и каждый сценарий, который сохраняется после изменения. И `openspec validate`, и `openspec archive` отклоняют блок, в котором потерян сценарий, всё ещё имеющийся в основной спецификации.
- Сохраняй всё, что дельта не упоминает, в существующем порядке основной спецификации
- Используй своё суждение, чтобы осмысленно объединить изменения

**Вывод при успехе**

```markdown
## Спецификации синхронизированы: <change-name>

Обновлены основные спецификации:

**<capability-1>**:
- Добавлено требование: «Новая функция»
- Изменено требование: «Существующая функция» (добавлен 1 сценарий)

**<capability-2>**:
- Создан новый файл спецификации
- Добавлено требование: «Другая функция»

Основные спецификации обновлены. Изменение остаётся активным — архивируйте его после завершения реализации.
```

**Ограничения**
- Перед изменениями читай и дельта-спецификации, и основные спецификации
- Сохраняй существующее содержимое, не упомянутое в дельте
- Никогда не копируй файл дельты в основную спецификацию как есть: объединяй содержимое, сохраняя структуру из справочника формата основной спецификации, без заголовков операций дельты
- Если что-то неясно, попроси уточнение
- По ходу работы показывай, что меняешь
- Операция должна быть идемпотентной: повторный запуск даёт тот же результат
- Используй только `artifactPaths.specs.existingOutputPaths`; никогда не определяй дельта-спецификации по посторонним артефактам
- Соблюдай переданное вызывающей стороной подмножество `existingOutputPaths`; никогда не расширяй его обратно до полного списка
- При прямой синхронизации запрашивай инструкции specs один раз; при вызове из архивирования повторно используй переданный снимок
- При ненулевом коде ответа или невалидном JSON инструкций specs остановись до любой записи основных спецификаций
- Правила артефактов ограничивают только записываемые спецификации и никогда не копируются в выходные файлы
