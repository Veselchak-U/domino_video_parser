## Context

Мотивация — [proposal.md](proposal.md). `PreparedObservation.finish` сейчас уничтожает частичный набор имён, записывая `None`. CPU `ScreenRecognizer._text` и GPU `DirectMLAdapter.text` отбрасывают строки с уверенностью ≤0.8 до возврата. `ParseManager._names` выбирает только полные наборы; отчёт содержит реконструированные коны, но не попытки OCR. GPU worker вызывает `finish(adapter.text)`, поэтому новый контракт должен пройти через оба пути и IPC.

## Goals / Non-Goals

**Goals:** сохранить наблюдаемую причину отказа и связанный участок без повторного OCR и накопления изображений в памяти.

**Non-Goals:** определять истинное написание имени из ошибочного OCR или считать любой кратковременный отказ основанием для запрета экспорта.

## Decisions

### 1. Структурированный результат OCR

Ввести внутреннее значение результата с исходными строками и их уверенностью; принятый текст строится по прежнему условию `confidence > 0.8`. Для имеющегося текстового вызова сохранить делегирование через новый результат. `finish` использует структурированный контракт, проверяет формат и добавляет сериализуемые метаданные попыток в наблюдение: поле, место/команда, область нормализованного кадра, коэффициент увеличения, строки, принятый текст, причина. Допустимая полная модель `names` остаётся прежней.

Альтернатива — логирование непосредственно в OCR worker — не связывает отказ с конечной ошибкой партии и даёт множество лишних файлов. Общий контракт обеспечивает одинаковые диагностические причины на CPU и GPU.

### 2. Выбор после проверки партии

Отдельный `RecognitionDiagnostics` получает наблюдения и интервалы партии/конов, выбирает диагностируемые поля по правилам delta-spec и формирует записи. Он не владеет наблюдениями и не выполняет файловый ввод/вывод. Для имён выбирается наиболее полный набор, при равенстве — первый по времени; показываются его пустые и повторяющиеся позиции. В предупреждении счётчика принимаются все попытки партии; для итогового счёта используются интервалы `_check_scores`. Корректные ручные имена устраняют соответствующую диагностику.

Связь с причиной ошибки делается через типизированные данные отказа реконструкции, а не через сравнение русских строк сообщения. Только ошибки OCR получают образцы; отсутствие исходных сведений для реконструкции хода не объявляется ошибкой чтения счётчика.

### 3. Повторное извлечение выбранного кадра

Передавать по IPC только метаданные, без PNG и полных кадров. После выявления ошибки `VideoReader` извлекает кадр по сохранённому presentation timestamp: seek к предшествующему ключевому кадру и декодирование до точного timestamp. Если исходный кадр не найден, сообщить отказ приложения образца вместо другого кадра. Нормализация и правила области/масштаба повторяются из общего профиля `ScreenRecognizer`; повторного OCR нет. Менеджер вызывает эти узкие операции согласно карте ответственности в proposal.

Альтернатива — сохранять все неуспешные участки во время чтения — требует памяти или большого числа промежуточных файлов. Дополнительное чтение нескольких кадров оправдано только при окончательной диагностике.

### 4. Публикация PNG и расширение JSON

Добавить `recognition_diagnostics` в запись партии. В каждой записи — `field`, `seat`/`team`, `position`, `round` при наличии, `time`, `raw_rows`, `accepted_text`, `threshold`, `reason`, `sample` (`path`, `time`) либо null и `sample_error` при сбое. Образец одного поля партии переиспользуется для повторных ошибок; его timestamp хранится отдельно от timestamp конкретной ошибки.

`ExportStorage` атомарно пишет бинарный PNG в `report/samples/<sha256-png>.png` через временный файл и замену. Вначале публикуются образцы, затем существующим атомарным методом JSON. Имя по содержимому предотвращает изменение пикселей, на которые ссылается старый JSON, если публикация нового отчёта не удалась. Автоматического удаления образцов нет. Пути строятся самим приложением и остаются внутри `samples`.

В реализации координатор `RecognitionSamples` проверяет хеш источника, вызывает точное чтение кадра и публикацию PNG, переиспользуя один нормализованный кадр для нескольких полей одного таймкода. Метаданные области и масштаба хранятся в попытке; общий `ScreenProfile` задаёт одинаковые области при распознавании и приложении образца. CPU/GPU возвращают `OCRResult`, а прежние методы текстового чтения делегируют ему фильтрацию.

## Risks / Trade-offs

- Повторное декодирование замедляет ошибочные запуски → ограничить выбор одним участком на поле партии, извлекать кадр один раз для нескольких участков одного timestamp.
- Источник исчез или изменился → ошибка получения образца сохраняется отдельно; неверный кадр не выдаётся за доказательство. До извлечения проверять SHA-256 источника относительно уже вычисленного хеша.
- Старые PNG остаются на диске → ограниченное число новых образцов на запуск, повторное использование идентичного содержимого; очистка вне объёма.
- Высокая уверенность не гарантирует правильное имя → сохраняется прежний контракт; улучшение модели отдельно.

## Migration Plan

Добавляемые поля отчёта и каталог образцов не требуют миграции игровых журналов. Обновить README с примером сообщения и открытием PNG. Проверить весь pytest-набор, OpenSpec и локальную диагностику текущего видео. Откат реализации прекращает создание дополнительных полей/PNG; существующие отчёты и образцы сохраняются.
