# Правила ревью

Эти правила применяются к новым изменениям. Они не утверждают, что в проекте
уже существуют перечисленные архитектурные роли, и не требуют массовой
перестройки демонстрационного приложения.

Текущий состав проекта и зависимостей указан в [контексте](../../AGENTS.md)
и [pubspec.yaml](../../pubspec.yaml). Не требуй библиотек или классов, которых там нет.

## 1. Dart

- Неизменяемые поля делай final. Мутабельное состояние оставляй только там,
  где оно необходимо для поведения или жизненного цикла.
- Не мутируй полученные коллекции: создавай копию.
- Используй required для обязательных параметров. Nullable допустим только
  при достижимом состоянии или подтверждённом контракте данных.
- Не добавляй nullable-зависимость без полноценного режима работы без неё.
- Не применяй оператор ! без проверки; используй явную обработку отсутствия значения.
- Взаимоисключающие варианты с разным обязательным содержимым выражай отдельными
  типами или sealed-вариантами, а не набором конфликтующих nullable-полей.
- Типизируй callbacks; не используй dynamic и голый Function без обоснования.
- Значения enum называй в camelCase; при разборе внешних данных обрабатывай
  неизвестные значения согласно контракту.

### Бизнес-логика и тестируемость

Нетривиальную логику фичи оформляй как методы объектов с явными зависимостями,
переданными через конструктор. Не размещай её в static-методах и функциях верхнего
уровня: такие связи труднее подменять в тестах.

Константы и конструкторы допустимы. Универсальные операции над примитивами,
не относящиеся к конкретной фиче, могут быть расширениями.
Не делай метод публичным только ради доступа теста.

## 2. Flutter

- По умолчанию используй StatelessWidget с const-конструктором и super.key.
  StatefulWidget оставляй для состояния и жизненного цикла UI; бизнес-логику
  отделяй от виджетов.
- Выделяй самостоятельные UI-фрагменты в приватные виджеты, а не методы,
  возвращающие Widget.
- Согласуй цвета и типографику с Theme.of(context). Повторяющиеся размеры
  оформляй как именованные значения. Не требуй отсутствующую дизайн-систему.
- Добавляй ключи по необходимости идентичности или тестирования, а не повсеместно.
- Следуй форматированию Dart и действующим правилам анализатора.
- Создание подписок, сетевые запросы и изменение состояния не выполняются в build
  и callbacks построения виджетов.
- После await перед обращением к UI проверяй актуальность жизненного цикла.
- Освобождай контроллеры и подписки у их владельца.
- Перестраивай только необходимую часть UI, используй const где возможно.

## 3. Модели и внешние данные

- Модель внешних данных содержит только поля, которые клиент читает, отправляет
  или обязан сохранить.
- Обязательность, nullable и ограничения значений сверяй с подтверждённым
  контрактом и достижимыми состояниями клиента.
- Не копируй полную серверную схему без необходимости.
- Не добавляй миграции и поддержку старых форматов для ещё не выпущенной фичи
  без явного требования совместимости.
- Обрабатывай все варианты состояний; не скрывай неизвестный вариант
  бесконтрольным значением по умолчанию.
- Если генерация будет согласована и подключена, не правь её результат вручную.
  Сейчас генераторы в проекте не настроены.

## 4. Архитектура и зависимости

Разделяй бизнес-логику, доступ к данным и отображение по мере появления
нетривиальной функциональности. Не создавай пустые слои или каталоги ради шаблона.

- Бизнес-логика зависит от контрактов, а не от UI и конкретного хранилища.
- Реализация доступа к данным реализует контракт; UI не обращается к ней напрямую.
- Контракты доступа не разделяются по физическому источнику: источник —
  деталь реализации.
- Сериализацию внешних данных отделяй от бизнес-моделей. Обоснованный компромисс
  для небольшой фичи явно фиксируй в проектном решении.
- Если интерфейс и реализация имеют разные зависимости по слоям, разнеси их.
  Перенаправляющая фабрика не должна скрыто затягивать зависимость на внешний слой.
- Не раскрывай наружу больше зависимостей, чем требуется потребителям.
- Не передавай короткоживущее состояние долгоживущему объекту без явного
  согласования времени жизни.
- Диалоги, навигация и сообщения пользователю относятся к UI. Бизнес-операция
  возвращает результат или ошибку.
- Ограничения доступности функции вычисляй в одном месте, не повторяй
  проверки окружения у каждого потребителя.

### Ответственности

До создания или существенного расширения объекта с состоянием определи:

| Ответственность | Что проверить |
|---|---|
| Состояние | Кто единственный владелец и кто публикует изменения |
| Хранение | Кто читает, записывает и определяет атомарность |
| Объединение данных | Кто вычисляет итоговую модель |
| Очистка | Кто определяет устаревание и удаление |
| Синхронизация | Кто отправляет данные и применяет ответ |
| UI-эффекты | Кто показывает результат пользователю |

Объект, который владеет состоянием и реализует ещё три или более перечисленных
обязанностей, раздели либо обоснуй исключение в проектном решении.
Координатор определяет порядок вызовов, но не содержит все алгоритмы.

## 5. Состояние и асинхронность

- Преобразование состояния не должно иметь скрытых побочных эффектов.
- Подписчик должен получать корректное начальное состояние, не дожидаясь
  случайного будущего события.
- Не пересоздавай долгоживущие потоки при каждом чтении.
- Разделяй независимые причины отказа: жизненный цикл, конкурентный запуск,
  отсутствие данных и ограничения окружения.
- Не выноси условие только из-за длины; имя выделенного условия должно раскрывать решение.
- Флаг выполнения устанавливай и сбрасывай в одной операции через finally.
- Асинхронная фаза возвращает обязательный результат; не передавай его через
  nullable-переменную, объявленную до try и читаемую после finally.
- После ожидания повторно проверяй ограничения, которые могли измениться.

## 6. Именование и стиль

| Роль | Суффикс |
|---|---|
| Изменение состояния | Controller |
| Преобразование данных и состояния в UI-модель | ViewModel |
| Хранение состояния в памяти | Provider или StateHolder |
| Оркестрация бизнес-операции | Manager |
| Контракт доступа к данным | Repository |
| Реализация контракта | RepositoryImpl |
| Адаптер хранения | Storage |
| Преобразование моделей | Mapper |
| Построение сложного объекта | Builder |

Это соглашения для новых классов, а не ссылки на готовые компоненты проекта.

- Файлы называй в snake_case; имена раскрывают роль и смысл значения.
- Расширениям добавляй суффикс X; определения общих типов не дублируй.
- Различай модель состояния, поток, будущий результат и UI-компонент в именах.
- Для типичных состояний модели предпочитай понятные именованные конструкторы.
- Порядок членов: статические поля → поля экземпляра final → конструкторы →
  публичные геттеры → публичные методы → приватные члены.
- Импорты группируй по SDK, внешним пакетам и коду проекта; окончательное
  требование задаёт [конфигурация анализатора](../../analysis_options.yaml).
- Не публикуй API исключительно ради теста: проверяй через настоящий публичный контракт.

## 7. Комментарии и источники поведения

Имена и декомпозиция должны объяснять действия кода. Комментарии нужны для
неочевидного решения, ограничения, единиц измерения или причины обхода.

- Не пересказывай очевидное; не оставляй закомментированный код.
- Незавершённую работу связывай с конкретной согласованной задачей.
- Ссылки ведут только на существующий ресурс проекта или проверенный публичный ресурс.
- Текущая спецификация описывает ожидаемое поведение, код — фактическую реализацию.
  Их расхождение нужно разрешить, а не объявлять один источник безусловно верным.

## 8. Безопасность, производительность и проверки

- Не записывай секреты в код или логи. Не считай клиентское веб-хранилище
  безопасным местом для секретов сервера.
- Проверяй внешние данные и освобождай ресурсы.
- Тяжёлые операции не должны блокировать интерфейс.
- Новая нетривиальная логика и исправления ошибок требуют тестов.
- Тестируй наблюдаемое поведение, включая ошибки и границы, а не детали реализации.
- Конвенции — [правила тестирования](UNIT_TEST_RULES.md).
- Для документации без изменения приложения достаточно проверки текста, ссылок
  и согласованности. Для изменённых исполняемых скриптов проверь синтаксис
  и затронутые сценарии.
- Для навигации, инициализации и других интеграционных границ выполни подходящую
  проверку работающего приложения; один анализатор их не подтверждает.
- Отдельные тесты не нужны для генерации, простого делегирования или переименования
  без изменения логики. Применимое исключение объясни в результате работы.

Проверяй итоговый diff и историю по [правилам коммитов](COMMIT_STRUCTURE_RULES.md).
Разделяй блокеры корректности и замечания к читаемости. В отчёте указывай только
реально выполненные проверки и явно называй ограничения.
