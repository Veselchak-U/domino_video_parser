# Правила тестирования

## Запуск

В проекте подключён flutter_test из Flutter SDK.
Текущий пример — [widget_test.dart](../../test/widget_test.dart);
зависимости перечислены в [pubspec.yaml](../../pubspec.yaml).

Из корня проекта:

```sh
flutter test
flutter test test/widget_test.dart
```

Существующий [скрипт тестов](../../tools/tests/run_unit_tests.sh) запускает весь
стандартный набор, включая widget-тесты. Несмотря на имя, он не выделяет отдельную
категорию unit-тестов и не исключает тесты по имени каталога.

```sh
bash tools/tests/run_unit_tests.sh
bash tools/tests/run_unit_tests.sh test/widget_test.dart
```

Аргументы передаются flutter test без изменений. Скрипт сам определяет корень
проекта; прямые команды Flutter предполагают запуск из корня.

## Размещение и структура

- Новые тесты создавай внутри [test](../../test/), по мере необходимости
  повторяя структуру тестируемого кода из [lib](../../lib/).
- Файлы тестов имеют суффикс _test.dart.
- Фикстуры и ручные подмены размещай рядом с использующими их тестами.
- Не создавай пустые каталоги и не предполагай наличие готовых наборов.
- Группируй тесты по публичному классу, операции и сценарию.
- Описания тестов пиши по-английски: ожидаемое поведение, а не реализация.
- Для объекта с несколькими зависимостями используй локальную фабрику с
  явными переопределениями параметров.

## Подмены зависимостей

Используй ручные реализации контрактов средствами Dart. Не требуй генераторы
моков и библиотеки, не подключённые к проекту.

- Подмена предоставляет результаты и ошибки, нужные проверяемым сценариям.
- При необходимости записывает вызовы и аргументы.
- Ненастроенный обязательный результат должен давать понятную ошибку.
- Неиспользуемые методы могут бросать UnimplementedError.
- Для проверки порядка действий несколько подмен могут вести общий журнал вызовов.
- Между тестами состояние подмен сбрасывается.
- Не добавляй тесту зависимости, которые он не использует.

## Асинхронность и время

- Ожидай завершения проверяемой операции или конкретных событий потока.
- Проверяй всю значимую последовательность событий, а не только последнее значение.
- Не используй произвольные задержки в секунды для ожидания результата.
- Если требуется обработать уже поставленные микрозадачи, явно дождись этого;
  это не заменяет ожидание настоящей асинхронной операции.
- В widget-тестах продвигай UI через методы tester, выбирая ожидание по сценарию.
- Не привязывай ожидания к текущим часам машины. Если логика зависит от времени,
  передавай источник времени как зависимость и задавай фиксированные значения
  или управляемое время в тесте.
- Проверяй границы интервалов, а не только средние значения.

## Данные и утверждения

- Простые неизменяемые фикстуры делай const; сложные данные собирай с разумными
  значениями по умолчанию и явными параметрами сценария.
- Для идентификаторов обычно достаточно стабильных строк; случайность не должна
  влиять на результат.
- Проверяй возвращаемое значение, состояние и существенные побочные эффекты.
- Проверяй, что нежелательные действия не произошли.
- При хранении данных проверяй и состояние в памяти, и сохранённое значение,
  а также восстановление после создания нового экземпляра.
- Используй стандартные matchers flutter_test; reason добавляй, когда причина
  неочевидна из утверждения.
- Не повторяй внутренний алгоритм в ожидаемом результате.

## Ресурсы и изоляция

- В setUp создавай независимое состояние; в tearDown освобождай ресурсы.
- Не разделяй мутабельные объекты между тестами.
- Не оставляй активные подписки, контроллеры и незавершённые операции.
- Проверяй через публичный контракт; не раскрывай продуктовый API только ради теста.

## Покрытие

Обязательны проверки новой нетривиальной логики, обработки ошибок, переходов
состояния и сохранения данных. Исправление ошибки сопровождай регрессионным тестом,
который падает до исправления.

Покрывай применимые пустые значения и коллекции, nullable-пути, исключения,
неизвестные входные данные и границы. Для каждого ожидаемого поведения должно
быть понятно, какое действие выполнено и что наблюдается.

Отдельный тест не нужен для простого делегирования, прямого копирования полей
или переименования без изменения логики. Для чистой правки документации
достаточно проверки текста и ссылок. Если меняется исполняемый скрипт,
проверь реальные успешные и ошибочные ветки его поведения.

Порядок работы при изменении приложения — в
[правилах OpenSpec](OPENSPEC_RULES.md).
Не объявляй весь набор успешным, если запускался только один файл.
