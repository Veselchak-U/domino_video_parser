## Context

См. proposal.md. Сейчас DeviceOCR владеет одним потоком и комплектом моделей. ObservationPipeline уже объединяет незавершённые CPU/GPU-задания в лимит 2*N, выдавая результаты по порядку. Прототип с отдельными процессами подтверждает ускорение на GTX 1060; прототип с потоками одного процесса аварийно завершился. Замеры сохранены в .analysis/gpu-wait/report.md; основные цифры продублированы в proposal, поскольку .analysis не входит в Git.

## Goals / Non-Goals

Сохранить точность и ограниченность очередей, исключить совместное нативное состояние GPU-моделей и не запускать второй комплект при неизвестном запасе памяти. Не менять декодирование, модели, частоту OCR и игровые контракты. Не вводить постоянный мониторинг памяти или повтор источника после ошибки во время распознавания.

## Decisions

1. GPU-модели создаются только в дочерних процессах spawn. У каждого один комплект и последовательная очередь. DeviceOCR возвращает обычные Future наблюдений, направляя очередное задание процессу с меньшим числом незавершённых работ. Счётчики уменьшаются и при ошибках. Родитель не загружает модели. Потоковый вариант исключён из-за измеренного нативного сбоя; независимые процессы дают изоляцию и перекрытие CPU-части OCR.
2. CLI --gpu-workers auto|1|2; auto и 2 выбирают максимум два с одинаковой проверкой памяти. Значение 1 удобно для ограничения памяти и сравнения. В CPU-режиме параметр не вызывает ни моделей, ни телеметрии. Выбор пересчитывается для каждого видео.
3. Свободную память брать из nvidia-smi memory.free только для однозначно сопоставленного адаптера DirectML 0. Идентификаторы DXGI VendorId/DeviceId/SubSysId сопоставлять с PCI-идентификаторами строк nvidia-smi; при нескольких подходящих строках не выбирать первую. Дополнительно проверять положительные total и согласованность free <= total. Таймаут команды 3 сек, запуск без окна, shell=False. Отсутствие утилиты, N/A, AMD/Intel или неоднозначность дают unknown, затем один GPU-процесс. Не выдавать DXGI DedicatedVideoMemory (ёмкость) или бюджет отдельного процесса за глобальную свободную память.
4. До запуска первого процесса для допуска двух требуется >=2048 MiB свободной памяти: два ориентировочных бюджета по 896 MiB и резерв 256 MiB. После успешной пробы первого и перед вторым повторный снимок должен показывать >=1152 MiB (896+256). После пробы второго должно оставаться >=256 MiB; иначе второй закрывается. Все границы включительные. Это консервативная эвристика по замерам, а не гарантия максимального расхода моделей; объяснить в README. При unknown на любой проверке ограничить одним. Первый процесс допускается без телеметрии и проверяется фактическим запуском всех моделей.
5. Первый процесс выполняет прежнюю пробу трёх моделей. Его неудача сохраняет auto→CPU и gpu→ошибка. Неудача или аварийный выход второго до чтения видео означает закрытие второго и повторную проверку первого; если первый исправен, продолжить им. Если нет — прежняя политика недоступности GPU. Число процессов печатается после завершения выбора: «OCR: GPU (DirectML, адаптер 0), процессов: 2» либо 1 с причиной ограничения. Не менять строку процента/скорости.
6. Инициализация ограничена 60 сек на процесс. Собственный владелец multiprocessing.Process и канала IPC позволяет обнаруживать exitcode и ограничивать остановку без использования частных атрибутов ProcessPoolExecutor. При отмене/ошибке прекратить подачу, отменить ещё не начатые задачи, дать 5 сек на остановку каждого процесса, затем terminate/join и при необходимости kill/join. Все pending Future должны завершиться результатом, отменой или исключением. Обычный корректный результат не ограничивать таймаутом вычисления. Setup GPU должен вызывать пробу через импортируемую точку входа с __main__-защитой, а не создавать spawn-процессы из stdin-скрипта.

## Risks / Trade-offs

Показ прогресса: ConsoleProgress.start запускает отсчёт и выводит имя, но не рисует строку и не запускает её обновление до сообщения о выбранном backend. Отдельный явный сигнал готовности от manager после сообщения OCR активирует отображение с фактическим прошедшим временем; не распознавать готовность по содержимому текста. Вызовы update до этого сохраняют состояние без вывода. Finish при ошибке инициализации всё равно печатает итоговую строку с ошибкой и прошедшим временем. Проверить TTY и перенаправленный вывод, CPU/auto/gpu, медленную инициализацию и ошибку до сигнала готовности. Частоту обновлений после активации и расчёт скорости не менять.

- [Память может измениться после снимка, модели выделяют буферы позже] → резерв, ограничения очереди и прежний отчёт об ошибке источника при runtime OOM; без обещания полного предотвращения нехватки памяти.
- [На AMD/Intel нет поддержанной телеметрии] → один DirectML-процесс с явной причиной; расширение провайдеров памяти отдельно.
- [Сбой второго процесса затрагивает драйвер] → повторная проба первого и прежняя политика device вместо ложного успешного старта.
- [IPC добавляет копирование областей] → общий лимит 2*N сохраняется, измерить полный контрольный запуск после реализации.
- [3 GB почти заполнены двумя процессами] → пороги допуска, параметр 1, повторные снимки и фактические замеры; не выбирать число по числу CPU.

## Migration Plan

После согласования написать падающие тесты выбора памяти и жизненного цикла, реализовать отдельные компоненты, затем интегрировать CLI/pipeline и GPU-установку. Проверить Windows module/EXE/BAT, отсутствие рекурсивного spawn, ошибки и отмену. Сравнить один и два процесса на контрольном видео с полным эталоном JSON. Запустить весь pytest/Ruff/OpenSpec, обновить README и архивировать изменение. Пользовательские JSON не мигрируются. Для эксплуатационного ограничения используется --gpu-workers 1, для CPU — --device cpu.

Источники API: [DXGI_ADAPTER_DESC](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ns-dxgi-dxgi_adapter_desc), [NVIDIA SMI](https://docs.nvidia.com/deploy/nvidia-smi/index.html). DXGI-идентификаторы описывают устройство, но не заменяют замер свободной памяти.

## Validation adjustment

2026-09-29 после освобождения приложений реальная свободная память оставалась ниже 2048 MiB. Пользователь явно разрешил проверить два GPU-процесса на полном видео через стенд с подменой только снимка памяти. Порог приложения не меняется. Результаты такого стенда отделяются от реальных запусков auto, выбравших один процесс, и не объявляются подтверждением автоматического допуска двух на этой машине.
