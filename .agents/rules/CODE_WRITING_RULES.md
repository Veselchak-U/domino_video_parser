# Чеклист написания кода

Подробное обоснование — [правила ревью](REVIEW_RULES.md).
Текущий стек — [контекст проекта](../../AGENTS.md).
Список зависимостей — [pubspec.yaml](../../pubspec.yaml).

## Перед изменением

- Прочитай затрагиваемый код, существующие тесты и связанные спецификации.
- Для изменения поведения соблюдай [процесс OpenSpec](OPENSPEC_RULES.md).
- Найди реальные места использования по [правилам поиска](TOOL_USAGE_RULES.md).
- Следуй существующей структуре; не ссылайся на несуществующие модули или инструменты.

## Dart и модели

- Предпочитай final; мутабельное состояние требует реальной необходимости.
- Копируй внешние коллекции перед изменением.
- required — для обязательных данных; каждый nullable-путь должен быть достижим
  и обработан. Не применяй ! без проверки.
- Разделяй варианты с разными обязательными данными на типы.
- Типизируй callbacks; избегай dynamic без обоснования.
- Нетривиальную бизнес-логику размещай в методах объектов с явными зависимостями.
- Внешние модели описывают используемый контракт, а не всю серверную схему.
- Проверяй неизвестные значения и числовые границы.
- Не вводи совместимость со старым форматом, который ещё не использовался.

## Flutter и состояние

- По умолчанию StatelessWidget, const и super.key. Состояние UI и его жизненный
  цикл могут требовать StatefulWidget.
- UI-фрагмент выделяй в отдельный приватный виджет.
- Цвета и текст согласуй с Theme.of(context); повторяющиеся размеры именуй.
- Не запускай подписки и побочные эффекты в build или callbacks построения.
- Бизнес-логика отделена от UI; диалоги и навигация остаются в UI.
- У долгоживущих потоков должен быть определён владелец и начальное состояние.
- Отменяй подписки и освобождай контроллеры.
- После await проверяй актуальность UI; сбрасывай флаги выполнения через finally.

## Архитектура

- Бизнес-логика зависит от контрактов, а не конкретного хранилища.
- Зависимости передавай явно; время жизни зависимости соответствует владельцу.
- Для нетривиального объекта с состоянием составь карту ответственности.
- Состояние вместе с тремя и более дополнительными обязанностями требует
  разделения или явного архитектурного обоснования.
- Именуй классы по роли согласно правилам ревью.
- Не создавай дополнительные слои, публичные типы и зависимости ради теста.
- Не дублируй определения моделей и проверки доступности функций.

## Проверка правки

1. Проверь форматирование только затронутых Dart-файлов без записи.
   Если версия форматтера создаёт посторонние изменения, выясни причину
   и не переписывай проект целиком.
2. Примени форматирование к согласованному набору файлов.
3. Для автоматических исправлений сначала используй dart fix с --dry-run
   и одним явным путём; применяй только относящиеся к задаче исправления.
4. Выполни flutter analyze.
5. Запусти соответствующие тесты по [правилам тестирования](UNIT_TEST_RULES.md).
6. Для изменённой интеграционной границы проверь работу приложения.
7. Сверь итоговые изменения с [правилами ревью](REVIEW_RULES.md).

Пример проверки существующего файла из корня проекта:

```sh
dart format --output=none --set-exit-if-changed lib/main.dart
dart fix --dry-run lib/main.dart
flutter analyze
```

Список файлов выбирай по задаче, а не копируй пример вслепую.
Не откатывай чужие изменения и не применяй массовые исправления без просмотра.
Продуктовые генераторы сейчас не настроены; не запускай вымышленные команды генерации.

Для чистой правки документации проверяй текст и ссылки; сборка приложения
не обязательна. При изменении скрипта проверь его синтаксис и поведение.

## Завершение

- Нет новых секретов, утечек ресурсов и необработанных ошибок.
- Проверены успешный, ошибочный и граничный сценарии затронутой логики.
- Имена и комментарии соответствуют коду.
- Указаны реальные результаты проверок и непроверенные области.
- Если готовятся коммиты, их состав отвечает [правилам истории](COMMIT_STRUCTURE_RULES.md).
