Предложи новое изменение — создай изменение и все артефакты за один проход.

**Граница процесса**: Этот скилл создаёт артефакты планирования и сам не
редактирует код. Явный вызов openspec-propose или запрос только на план
заканчивается представлением артефактов. Если скилл используется как этап
явно заказанной реализации, после подготовки и проверки артефактов продолжи
через openspec-apply-change в том же запросе, без повторного ОК.
Выбор процесса, разрешения и блокеры определены
[правилами OpenSpec](../../rules/OPENSPEC_RULES.md), чтение —
[правилами инструментов](../../rules/TOOL_USAGE_RULES.md).
При использовании внутри реализации сначала проверь короткий путь исправления
существующего контракта по правилам OpenSpec; явный вызов этого скилла
остаётся планированием. Продолжай соответствующий существующий change,
вместо создания дубликата. Не сужай заказанное поведение молча.

Я создам изменение с артефактами, определёнными вашей схемой. Для стандартной схемы spec-driven это:
- proposal.md (что и зачем)
- `specs/<capability-path>/spec.md` (что система должна делать — дельта, а не основная спецификация)
- design.md (как)
- tasks.md (шаги реализации)

`<capability-path>` — каталог спецификации относительно `specs/` (например, `user-auth` или `identity/user-auth`). Сохраняй полный путь существующей возможности; новые возможности размещай по принятой в проекте структуре.

**Выбор хранилища:** Если пользователь указал хранилище (store — отдельный репозиторий OpenSpec, зарегистрированный на этой машине) или работа находится в нём, выполни `openspec store list --json`, чтобы узнать идентификаторы зарегистрированных хранилищ. Затем передавай `--store <id>` командам чтения и записи спецификаций и изменений (`new change`, `status`, `instructions`, `list`, `show`, `validate`, `archive`, `doctor`, `context`, `schemas`, `view`). После выбора сохраняй `--store <id>` до конца рабочего процесса. Все приведённые ниже примеры этих команд без указания хранилища сокращены: перед выполнением добавляй флаг. Например, выполняй `openspec status --change "<name>" --json --store "<id>"`, а не приведённый ниже вариант без хранилища. Другие команды этот флаг не принимают. Подсказки в выводе команд уже содержат флаг; сохраняй его в последующих вызовах. Если хранилище не выбрано, команды работают с ближайшим локальным корнем `openspec/`.

**Входные данные**: Запрос пользователя должен содержать имя изменения в kebab-case ИЛИ описание того, что он хочет создать.

**Шаги**

1. **Пойми запрос и уточни существенную неоднозначность**

   Если ясных входных данных нет, задай открытый вопрос без готовых вариантов ответа:
   > «Над каким изменением вы хотите работать? Опишите, что нужно создать или исправить.»

   Из описания выведи имя в kebab-case (например, «добавить аутентификацию пользователей» → `add-user-auth`).

   **ВАЖНО**: НЕ продолжай, пока не поймёшь, что пользователь хочет создать.

2. **Определи схему рабочего процесса**

   Используй настроенную схему по умолчанию, если пользователь явно не попросил другой процесс.

   **Используй другую схему, только если пользователь:**
   - Явно назвал конкретную схему → используй `--schema <schema-name>`
   - Просит «показать рабочие процессы» или спрашивает, какие процессы существуют → определи действующий корень командой `openspec context --json` из текущего рабочего каталога. Если пользователь явно выбрал зарегистрированное хранилище, используй `openspec context --json --store "<store-id>"`. Затем выполни `openspec schemas --json` с рабочим каталогом, равным полученному `root.path`, и дай пользователю выбрать. Это сохраняет корни, выбранные локальным указателем `store:` или глобальным `defaultStore`; при явном выборе зарегистрированного хранилища также добавь `--store "<store-id>"` к `openspec schemas --json`. Если context сообщает только `no_openspec_root`, вместо этого выполни `openspec schemas --json` из текущего рабочего каталога. Не используй этот запасной вариант при некорректных или недоступных хранилищах.

   В остальных случаях не передавай `--schema`, чтобы сохранить настроенную схему по умолчанию.

3. **Продолжи соответствующий change или создай каталог изменения**

   Если соответствующий change уже существует, переходи к его status без
   повторного new change. Иначе создай заготовку командами ниже.

   Выбери ниже один вариант команды. Если выбрано зарегистрированное хранилище,
   добавь `--store "<store-id>"` к этой команде и каждой последующей команде
   OpenSpec ниже, которая принимает `--store`.

   С настроенной схемой по умолчанию:
   ```bash
   openspec new change "<name>"
   ```

   С явно запрошенной схемой:
   ```bash
   openspec new change "<name>" --schema "<schema-name>"
   ```
   Команда создаёт заготовку изменения с `.openspec.yaml` в области планирования, определённой CLI.

4. **Получи порядок создания артефактов**
   ```bash
   openspec status --change "<name>" --json
   ```
   Разбери JSON и получи:
   - `applyRequires`: массив идентификаторов артефактов, необходимых до реализации (например, `["tasks"]`)
   - `artifacts`: список всех артефактов; у каждого есть `status` и связи `requires` (идентификаторы артефактов, от которых он непосредственно зависит)
   - `planningHome`, `changeRoot`, `artifactPaths` и `actionContext`: контекст путей и области работы. Используй их, не предполагая, что пути находятся в текущем репозитории.

5. **Создай каждый артефакт из обязательного набора**

   Обходи артефакты в порядке зависимостей, начиная с тех, у которых нет незавершённых зависимостей:

   a. **Для каждого артефакта в состоянии `ready` (зависимости удовлетворены)**:
      - Получи инструкции:
        ```bash
        openspec instructions <artifact-id> --change "<name>" --json
        ```
      - JSON инструкций содержит:
        - `context`: контекст проекта (ограничения для тебя — НЕ включай в результат)
        - `rules`: правила конкретного артефакта (ограничения для тебя — НЕ включай в результат)
        - `template`: структура выходного файла
        - `instruction`: инструкции схемы для этого типа артефакта
        - `skipped`/`warning`: присутствуют, когда изменение объявляет skip_specs и этот артефакт создавать НЕЛЬЗЯ — прекрати его создание и выбери другой
        - `resolvedOutputPath`: разрешённый путь или шаблон для записи артефакта
        - `dependencies`: завершённые артефакты, которые нужно прочитать для контекста
      - Получи актуальное содержание завершённых зависимостей по правилам инструментов
      - Если поле `instruction` поручает создание конкретному скиллу или команде, вызови их вместо самостоятельной записи файла, затем проверь существование артефакта по `resolvedOutputPath`
      - Иначе создай файл артефакта по структуре `template` и запиши в `resolvedOutputPath`. Если `resolvedOutputPath` — glob-шаблон, выбери конкретный путь по `instruction`
      - Применяй `context` и `rules` как ограничения, но НЕ копируй их в файл

   b. **Продолжай, пока не будет существовать каждый артефакт обязательного набора, а не только `apply.requires`**
      - Обновляй status после записи артефактов, когда нужно получить готовность следующих; не повторяй запрос для неизменившегося состояния
      - Обязательный набор включает `applyRequires` и каждый артефакт, достижимый из них по связям `requires` в `status --json`: обходи их транзитивно (для spec-driven набор включает proposal, specs, design, tasks). Артефакты вне этого набора не трогай
      - `status` проверяет только существование файлов, поэтому `done` у артефакта из `applyRequires` НЕ означает, что его зависимости существуют: ранняя запись `tasks.md` помечает `tasks` как done, даже если `specs` ещё не создан. Строй обязательный набор по связям `requires` каждого артефакта, а не по его `status`: артефакт `done` по-прежнему перечисляет свои зависимости
      - Артефакт со `status: "skipped"` уже удовлетворяет требованиям: изменение объявляет `skip_specs` в `.openspec.yaml`, поэтому его файлов НЕ должно быть. Никогда не пытайся его создать
      - Создай каждый отсутствующий артефакт обязательного набора, затем проверь снова: создание одного может разблокировать другие
      - Пропускай артефакт, только если `status` уже сообщает `skipped` или его собственная `instruction` указывает условие создания: выполни `openspec instructions <artifact-id> --change "<name>" --json` и пропускай только при указании необязательности в поле `instruction` (например, «создавать только если…»). В spec-driven это допустимо для `design.md`; `specs` можно пропустить только по статусу `skipped`, указанному выше, никогда по собственному решению. Сообщи пользователю и не пересматривай принятое решение
      - Зависимости помогают выстроить работу, но не являются безусловным запретом: если обязательный артефакт всё ещё `blocked` только из-за пропущенной условной зависимости, всё равно создай его
      - Остановись, когда каждый артефакт обязательного набора имеет статус `done`, `skipped` или был сознательно пропущен

   c. **Если артефакт требует данных от пользователя** (контекст неясен):
      - Уточни недостающие существенные данные по правилам OpenSpec
      - Затем продолжай создание

6. **Покажи итоговый статус**
   ```bash
   openspec status --change "<name>"
   ```

**Вывод**

После завершения всех артефактов подведи итог:
- Имя и расположение изменения
- Список созданных артефактов с краткими описаниями, а также все пропущенные условные артефакты и причины пропуска
- Что готово: «Все артефакты, необходимые для реализации, готовы.»
- Для запроса только на план предложи openspec-apply-change. Для уже заказанной реализации сообщи «План подготовлен» и продолжи через скилл реализации, если нет существенного нерешённого вопроса.

**Рекомендации по созданию артефактов**

Объём текста соразмерен изменению: малая правка требует краткого описания,
а design объясняет техническое решение без повторения delta-spec.
Не сокращай обязательный набор артефактов и проверки контрактов CLI.

- Следуй полю `instruction` из `openspec instructions` для каждого типа артефакта: это определяющая инструкция даже для знакомых имён артефактов
- Если поле `instruction` предписывает использовать конкретный скилл или команду для создания артефакта, вызови их вместо прямой записи
- Схема определяет содержимое каждого артефакта — следуй ей
- Перед созданием новых артефактов читай артефакты зависимостей для контекста
- Используй `template` как структуру выходного файла — заполни его разделы
- **ВАЖНО**: `context` и `rules` — ограничения для ТЕБЯ, а не содержимое файла
  - НЕ копируй блоки `<context>`, `<rules>`, `<project_context>` в артефакт
  - Они направляют написание, но никогда не должны попадать в результат

**Ограничения**
- Не редактируй код средствами этого скилла. При явном вызове скилла или запросе только на план остановись после представления артефактов; при использовании как этапа заказанной реализации передай готовый change в openspec-apply-change без повторного разрешения.
- Создай каждый артефакт, от которого этап реализации зависит транзитивно, а не только идентификаторы из `apply.requires`
- После записи проверяй существование каждого файла артефакта, прежде чем перейти к следующему
