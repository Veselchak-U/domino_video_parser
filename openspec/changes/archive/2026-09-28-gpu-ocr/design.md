## Context

GTX 1060 3 ГБ, драйвер 560.94, Python 3.12. CPU ONNX Runtime 1.30.0; RapidOCR 1.4.4 уже имеет флаги det/cls/rec_use_dml. Его текущая фабрика SessionOptions явно не отключает memory pattern, а DirectML требует enable_mem_pattern=False и последовательное выполнение. Простого переключения флага недостаточно для надёжной интеграции.

## Goals / Non-Goals

Сохранить текущие модели, preprocessing, порог уверенности и частоту OCR, отделив исполнение моделей от визуальных алгоритмов. Подключить DirectML и проверить результат на реальном видео. Оптимизация моделей, снижение точности и пропуск кадров не входят в изменение.

## Decisions

1. DirectML выбран за совместимость с Windows/GTX 1060 без CUDA/cuDNN. Документация: https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html. DirectML поддерживается в режиме сопровождения; переход на WinML возможен позднее. CUDA не выбирается для первой версии из-за дополнительной матрицы версий и старого GPU.
2. Первым техническим этапом после тестов выбора режима выполнить проверку всех трёх моделей в отдельной .venv-gpu. Установить приложение и зависимости, заменить CPU-дистрибутив onnxruntime на onnxruntime-directml по инструкции RapidOCR, зафиксировать успешную версию в GPU requirements/скрипте. Не оставлять два дистрибутива с одинаковым модулем onnxruntime. RapidOCR декларирует CPU runtime в metadata: установка приложения после замены может вернуть его; скрипт установки должен явно выполнять замену последним шагом и проверять providers, а README объяснять это ограничение pip metadata. Рабочую .venv сохранить. run.bat выбирает готовую .venv-gpu при наличии, иначе .venv; --device cpu доступен и в GPU-среде. Аргументы пользователя в run.bat сохранить.
3. Локальный OCR adapter создаёт корректные DirectML-сессии и подключает их к существующей OCR обработке без правки site-packages и глобальной подмены ONNX Runtime. Проверить реальный provider каждой сессии и выполнить непустые входы детекции, классификации и распознавания. Во время контрольного запуска собрать ORT profiling для подтверждения GPU-операторов: наличие provider само по себе не доказывает исполнение всех операций на GPU. CPU fallback отдельных неподдерживаемых операторов допустим, полный незаметный переход на CPU — нет.
4. CPU этап выдаёт наблюдение и копии нужных crop-областей (без ссылок, удерживающих полный кадр). GPU этап последовательно выполняет OCR и завершает наблюдение. Единственный поток владеет моделями; конкурентных вызовов одной DML-сессии нет. CPU режим сохраняет существующий путь. Частота имён/счётчиков и дополнительные чтения табло при пустом столе сохраняются в обоих режимах.
5. Суммарное окно 32*N ограничивает кадры до выдачи; изображения и crop-задания вместе ограничить 2*N, готовые наблюдения без изображений отдельно. Backpressure применяется до декодирования следующего кадра. Для workers=1 CPU без дочернего пула; GPU может использовать один поток в родительском процессе. Ошибки отменяют ожидающие задания, завершают активные и освобождают ресурсы в finally.
6. Выбор auto проверяет функциональность, а не скорость. Если GPU медленнее CPU, это явно отражается в измерениях и рекомендуется --device cpu. Сравнить CPU и GPU одинаковыми входами минимум дважды, разделить инициализацию и основной проход, измерить общий wall time, RAM и VRAM доступными средствами. Полное равенство игрового JSON ручному эталону — критерий приёмки; расхождения OCR расследовать, не ослаблять проверки ради GPU.

## Risks / Trade-offs

- 3 ГБ VRAM → один комплект моделей, ограниченная очередь, обработка OOM как сбоя.
- Передача crops и малые входы могут съесть выигрыш → измерять полное видео, не обещать коэффициент ускорения.
- DirectML adapter 0 может быть встроенной графикой на другой машине → документировать выбор; auto означает работоспособный backend, не самый быстрый GPU.
- Численные различия → сравнение JSON и диагностик с CPU, сохранение порогов и моделей.
- Нативный вызов OCR может закончиться не мгновенно при Ctrl+C → прекратить подачу, дождаться активного вызова и закрыть очередь; не оставлять работающие потоки.

## Migration Plan

Сначала изолированный GPU запуск и фиксация зависимостей, затем тесты и интеграция. После проверки запускать через прежний run.bat с готовой GPU-средой. Для возврата к CPU использовать --device cpu или прежнюю .venv напрямую. Никаких изменений драйвера или миграции JSON.

## Реализация и измерения

Используется onnxruntime-directml 1.24.4, RapidOCR 1.4.4, GTX 1060 3 ГБ, драйвер 560.94. Проверка ORT profiling подтвердила GPU-операторы во всех трёх моделях: det 612 DML, cls 620 DML, rec 1364 DML и 48 вспомогательных CPU событий на пробном запуске. GPU backend не означает исполнение каждого оператора на GPU.

Адаптер сначала создаёт существующий RapidOCR с CPU-сессиями для штатной подготовки и metadata, затем заменяет только сессии тех же моделей на DirectML с правильными SessionOptions. Глобальные классы и site-packages не изменяются. Три модели прогреваются непустыми тензорами; fallback сессии отключён. После источника модели освобождаются в том же потоке, где созданы.

Полное контрольное видео длительностью 290,472 сек, 24 CPU процесса, отдельные последовательные subprocess-прогоны. Время ниже включает запуск интерпретатора и завершение процесса; таймер строки прогресса немного короче. Память — пиковая сумма RSS дерева процессов, а не уникальные физические страницы. VRAM — суммарная занятость всей видеокарты вместе с рабочим столом, не только приложением.

Среднее время CPU 104,310 сек, GPU 101,406 сек: сокращение времени 2,78%, существенного ускорения на этой карте не получено. Память процессов примерно 7,8 ГиБ против 0,9 ГиБ. Первый дополнительный GPU-прогон также дал эталонный JSON за 100 сек по консольному таймеру. Хеш видео остался 09d33287088535cfd2c06170d7741a38e008a2e8b60dc91c4f06a15ae9fbe065. Диагностические замеры находятся в игнорируемом .analysis/gpu-benchmark; не входят в поставку.

При реальной проверке run.bat обнаружены смешанные переводы строк после редактирования; нормализованы CRLF и добавлено Git-правило для BAT. Установочный скрипт проверяется через Windows PowerShell 5, использует stdin Python вместо чувствительного к кавычкам -c. Сообщение probe оставлено ASCII, чтобы кодировка cp1252 не превращала успешную проверку GPU в ошибку установки.

Финальные проверки: полный набор 192 passed in 39.85s; Ruff check и format --check для 28 файлов успешны; строгая валидация OpenSpec успешна. Реальный GPU workers=1 на трёх кадрах совпадает с CPU; полный GPU workers=24 проверен тремя прогонами. Windows PowerShell setup завершился успешно, готовая GPU-среда содержит только onnxruntime-directml 1.24.4; исходная CPU-среда сохраняет onnxruntime 1.30.0. Проверены BAT до готовности GPU-среды и после, а также Windows module/exe/BAT в полном наборе. Отдельный замер инициализации GPU (импорт, создание и прогрев моделей) составил 1,790 секунды; это не вычиталось из полных времён видео. Большую часть примерно 101 секунды занимает основной проход. Проверены diff и отсутствие случайных GPU-окружений/замеров в Git.
