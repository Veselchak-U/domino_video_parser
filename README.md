# Domino Video Parser

Консольное приложение Python для локального разбора записей экранной командной
игры «Козёл». На выходе — отдельный JSON `kozel-game-v1` для каждой завершённой
партии и диагностический отчёт для каждого видео.

Контракт синхронизирован с `domino_spec` версии `cf1f51f`. В `moves[].stone`
камень `a-b` всегда ориентирован слева направо: при ходе `left` со столом
соединяется половина `b`, при `right` — половина `a`. В раздачах `deal`
сохраняется запись от меньшей цифры к большей. Название формата — `kozel-game-v1`.
Старые JSON с другой ориентацией ходов могут не пройти новую проверку;
для обновления повторно обработайте исходные видео. Автоматической миграции нет.

Поддерживается визуальный интерфейс предоставленного образца: зелёный стол,
четыре игрока, светлые камни с точками, раскрытие оставшихся рук после кона.
Записи поворачиваются и масштабируются автоматически. Съёмка настоящего стола,
другие темы и интерфейсы не входят в поддерживаемый профиль.

## Установка

Нужен 64-битный Python 3.11 или новее. Из корня проекта в PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[test]"
```

PyAV содержит декодер: устанавливать FFmpeg отдельно не нужно. Модели OCR
поставляются внутри пакета `rapidocr-onnxruntime`; после установки приложение
обрабатывает видео без сети и без API-ключей. Системный Python здесь не изменяется.

## Запуск

На Windows можно использовать `run.bat` с теми же аргументами:

```powershell
.\run.bat --fish-variant withoutEggs --score-limit 50
```

BAT использует подготовленную `.venv-gpu`, если GPU-установка завершена,
иначе `.venv` в корне проекта, и передаёт код завершения
приложения. Относительные пути разрешаются от текущего каталога командной строки.
Справка: `.\run.bat --help`. Поместите видео в каталог `in` перед запуском;
результаты появятся в `out`. Входной каталог нужно создать самостоятельно.

Прямой запуск Python:

```powershell
.\.venv\Scripts\python.exe -m domino_video --fish-variant withoutEggs --score-limit 50
```

Другие входной и выходной каталоги:

```powershell
.\run.bat --input "C:\Videos" --output "C:\Results" --fish-variant withEggs --score-limit 101
```

Также доступна команда `.\.venv\Scripts\domino-video-parser.exe` с теми же аргументами.
`--input` по умолчанию равен `in`, `--output` — `out`; каждый можно переопределить
отдельно. Обязательны вариант рыбы (`withEggs`/`withoutEggs`) и лимит
(`50`/`101`). Они задают правила всех партий данного запуска, а не угадываются.
Разные правила требуют отдельных запусков. Пути с пробелами заключайте в кавычки.

Обрабатываются файлы непосредственно во входном каталоге, без вложенных папок,
в порядке имён без учёта регистра. Расширения: `.mp4`, `.mkv`, `.mov`, `.avi`,
`.webm`, `.m4v`, `.mpeg`, `.mpg`, `.ts`, `.mts`, `.m2ts` (регистр не важен).
Прочие файлы игнорируются. Пустой или недоступный входной каталог даёт ошибку и
код 1. Старый запуск с перечислением отдельных видео больше не поддерживается.

Прогресс в интерактивной консоли выводится под полным именем видео:

```text
[2/5] полное_имя_видео.mp4
  Обработано 10% за 15 сек скорость 2x
```

Вторая строка начинается с двух пробелов и обновляется каждую секунду, даже
если процент не изменился. Процент и время обработки файла выводятся целыми
числами. Время отсчитывается от вывода имени до записи отчёта, включает проверки
и сохранение; предварительное хеширование пакета в него не входит. На этапе проверки и сохранения
показывается 99%, а при успешной записи результатов и отчёта немедленно выводится
итог, например `  Обработано 100% за 135 сек скорость 2.15x`.
Скорость — отношение обработанного времени видео к прошедшему времени обработки.
Например, 100 секунд видео за 5 секунд дают `скорость 20x`. Скорость меняется
только при изменении целого процента (включая итоговые 100%); между такими
изменениями обновляется только время. До начала обработки выводится `скорость 0x`.
Дробная скорость округляется до двух знаков, конечные нули не выводятся.
Если длительность отсутствует в метаданных, сначала выполняется дополнительный
проход по временным отметкам видео. При перенаправлении вывода остаются начало,
итог и сообщения о сохранении/ошибках, без промежуточных обновлений.

Кадры одного видео распознаются несколькими процессами. По умолчанию число
процессов определяется на текущем компьютере по доступным логическим CPU
(на Windows максимум 61). Выбранное число выводится в начале запуска.
Для ограничения нагрузки используйте `--workers 4`; `--workers 1` включает
последовательную CPU-обработку. В CPU-режиме каждый процесс загружает свою модель OCR, поэтому
при большом числе ядер требуется больше памяти. Новые кадры подаются при
завершении любого задания; результаты выдаются в исходном порядке. В обработке
находится до 2 × N заданий с изображениями, общее окно ещё не выданных кадров
ограничено 32 × N (N — число процессов). При заполнении окна чтение ждёт ранние
результаты. Это ограничивает память и уменьшает простой за тяжёлыми OCR-кадрами.
Внутренние потоки OCR и OpenCV ограничены одним на процесс. Декодирование,
проверки и запись выполняются последовательно; постоянная загрузка всех ядер
и линейное ускорение не гарантируются.

### Видеокарта на Windows

Поддерживается DirectML на Windows 10/11 с DirectX 12, включая GTX 1060.
CUDA/cuDNN не нужны. После обычной установки выполните из корня проекта:

```powershell
powershell -ExecutionPolicy Bypass -File tools\setup_gpu.ps1
.\run.bat --device gpu
```

Скрипт создаёт отдельную `.venv-gpu`, устанавливает ONNX Runtime DirectML 1.24.4
и проверяет запуск трёх OCR-моделей. Только после успешной проверки `run.bat`
начинает выбирать эту среду. Прежняя `.venv` и системный драйвер сохраняются.
Модели поставляются с RapidOCR; после установки распознавание работает без сети.

`--device auto` (по умолчанию) использует GPU, если модели удалось запустить,
иначе выбирает CPU и сообщает причину. `--device cpu` принудительно отключает GPU.
`--device gpu` при недоступности GPU выдаёт ошибку; режим печатается как
`OCR: GPU (DirectML, адаптер 0)` или `OCR: CPU`.
На других ОС доступен CPU. Auto проверяет работоспособность, а не быстродействие.

В GPU-режиме `--workers` задаёт CPU-процессы подготовки кадров, а один или два отдельных процесса
со своими OCR-моделями работают на GPU. Очередь кадров и областей OCR ограничена совместно.
При сбое GPU текущий файл завершается с отчётом об ошибке; следующий файл заново
проверяет устройство. Автоматического повторного распознавания текущего файла нет.
Используется адаптер DirectML 0, который на ноутбуке может быть встроенной графикой.
Ускорение зависит от видеокарты и записи; для сравнения используйте `--device cpu`.

Число GPU-процессов выбирается отдельно:

```powershell
.\run.bat --gpu-workers auto
.\run.bat --gpu-workers 1
```

`--gpu-workers auto` (по умолчанию) и `--gpu-workers 2` допускают до двух
процессов с проверкой памяти; `1` всегда ограничивает одним. Значение `2`
не обходит проверку памяти. В CPU-режиме параметр не задействует GPU.
Фактическое число и причина ограничения выводятся в сообщении OCR.

Для двух процессов нужно минимум 2000 МиБ свободной видеопамяти до загрузки
моделей, 1152 МиБ после пробы первого и 256 МиБ после пробы второго.
Проверка повторяется для каждого видео. Если второй процесс не запустился,
программа повторно проверяет первый и продолжает им, если он исправен.

Телеметрия поддерживается для NVIDIA через установленную с драйвером
`nvidia-smi`, после однозначного сопоставления с DirectML-адаптером 0.
При неизвестной памяти, ошибке опроса или неподдержанной телеметрии (включая
AMD/Intel) используется один GPU-процесс. Память может измениться после замера;
пороги не гарантируют отсутствие нехватки памяти во время распознавания.
На GTX 1060 3 ГБ два процесса в эксперименте сократили время контрольного видео
со 100 до 75 секунд, но заняли до 2822 МиБ общей видеопамяти. Постоянные 100%
загрузки GPU не гарантируются.

До выбора OCR выводится только имя файла. Строка прогресса появляется после
сообщения OCR; время и скорость учитывают и инициализацию, начиная с вывода имени.

RapidOCR указывает CPU-пакет `onnxruntime` в метаданных зависимостей, хотя работает
с `onnxruntime-directml`. Скрипт заменяет его последним шагом. Поэтому `pip check`
в GPU-среде может сообщать об отсутствующем `onnxruntime`; устанавливать его рядом
с DirectML нельзя: они предоставляют один модуль. После переустановки приложения
повторно выполните `tools\setup_gpu.ps1`. Для запуска исходной CPU-среды напрямую:

```powershell
.\.venv\Scripts\python.exe -m domino_video --device cpu --fish-variant withoutEggs --score-limit 50
```

Каждый входной файл независим. Партия, разрезанная на несколько файлов,
автоматически не склеивается. Несколько полных партий в одном видео поддерживаются.

Имена результатов: `2026-09-28-13-58-source-001-game-001.json`,
`report/2026-09-28-13-58-source-001-report.json`. После `source` — позиция входного
файла, после `game` — номер партии.

Дата берётся из имени видео, если оно содержит корректную строку
`YYYY-MM-DD-HH-MM`, например `Record_2026-09-28-13-58-19.mp4`. Секунды в этом
случае отбрасываются. Если такой строки нет, используется `creation_time`
контейнера, затем первого видеопотока. Метаданные с часовым поясом переводятся
в локальную таймзону операционной системы на дату записи. Имена всегда без `Z`
и смещения пояса, например `2026-09-28-14-05-source-001-game-001.json`.
Время из имени и метаданные без пояса считаются уже локальными и сохраняются
без пересчёта; даты папок не используются.

Если даты нет или метаданные прочитать невозможно, подставляется текущее время
в локальной зоне ОС с секундами и миллисекундами:
`2026-09-28-18-04-03-007-source-001-game-001.json`.
Оно фиксируется один раз на видео и используется для всех его партий и отчёта.
Поле `recording_time` отчёта содержит источник (`filename`, `container.creation_time`,
`video.creation_time` или `current_time`), исходное значение, основу имени и причину
подстановки. Даты файловой системы не используются. Ошибки самого видео по-прежнему
приводят к диагностике, даже если время удалось подставить.

Если имя содержит несколько разных корректных дат, создаётся
`report/undated-source-001-report.json` с описанием неоднозначности без игрового JSON.
Диагностические отчёты записываются в подпапку `report` выбранного каталога
`--output` (по умолчанию `out/report`). Подпапка создаётся автоматически. Отчёт
с совпадающим именем при повторной обработке атомарно перезаписывается. Старые
отчёты в корне выходного каталога автоматически не перемещаются и не удаляются.
Существующий игровой JSON с совпадающим именем атомарно заменяется после успешной
проверки новой партии. При ошибке проверки или замены прежний файл сохраняется.
Лишние файлы партий от предыдущих запусков автоматически не удаляются.
При сбое итоговая строка заканчивается на `скорость Zx — ошибка`;
только ` — ошибка` выделяется красным в поддерживающем цвет терминале.
При перенаправлении вывода цветовые коды отсутствуют.
Код завершения 0 означает полный успех, 1 — проблему чтения,
распознавания, проверки или записи, 2 — неверные аргументы.

## Достоверность и отчёты

Программа читает камни, имена, индикатор хода и счёт локально. Начальные руки
восстанавливаются из сыгранных камней и раскрытых остатков. Анимации фильтруются,
пасы проверяются по рукам, неоднозначные события решаются только при единственном
допустимом варианте. Единственный не попавший на устойчивый кадр последний камень
может быть восстановлен по полному набору, остатку, исполнителю и правилам.

Каждый итог проверяется JSON Schema и воспроизведением: все 28 камней, очередь,
заход, края, обязательные пасы, выход/рыба, штрафы, забор, яйца и завершение партии.
Показания табло сверяются с вычисленным счётом. Неоднозначный или неполный журнал
не экспортируется. Отчёт содержит таймкоды, наблюдаемые события, кандидатов
исполнителя, остатки и ошибки; это **не** документ `kozel-game-v1`.

Автоматическое распознавание проверяется на предоставленном образце. Это не
гарантия точности на произвольных видео: скрытые точки, перекрытия, монтаж,
нечитаемые имена и отличия правил могут потребовать исправления либо другой записи.
JSON сохраняет экранные имена (в том числе `You`); при необходимости задайте
читаемые имена через исправления.

При отказе чтения имён, счётчиков камней или итогового счёта запись партии
содержит `recognition_diagnostics`: поле, место игрока/команду, фактический
таймкод OCR, исходные строки `raw_rows` с уверенностью, принятый текст,
порог и причину отказа. Например, в консоли:

```text
Партия 1: имя, место 2 (слева сверху), 40.00 сек — низкая уверенность OCR; OCR: «MnX@/by» (72.5%), порог > 80%; образец: out\report\samples\<sha256>.png
```

PNG содержит именно участок выбранного кадра, который подавался в OCR.
Чтобы открыть его, соедините каталог JSON-отчёта с относительным путём
`sample.path`, например `out/report/samples/<sha256>.png`.
`sample.time` указывает таймкод образца. При повторных ошибках одного поля
в нескольких конах они используют один образец на партию; его таймкод может
отличаться от таймкода конкретной ошибки. Идентичные PNG переиспользуются при
повторном запуске, старые образцы автоматически не удаляются.

Причины различают пустой OCR, низкую уверенность (принимаются только строки
строго выше 80%), неверный формат, повтор имени и отсутствие пригодного кадра.
Если извлечь или сохранить PNG невозможно, `sample` равен null, подробности
сбоя находятся в `sample_error`, а запуск завершается с кодом 1. Устранившееся
при последующем чтении или исправлении поле не создаёт образцов. Нечитаемый
счётчик сам по себе остаётся предупреждением и не запрещает экспорт.
Высокая уверенность OCR не гарантирует правильного написания имени.

## Исправления

Скопируйте объект `corrections_template` из отчёта в отдельный JSON и передайте
`--corrections corrections.json`. SHA-256 связывает исправления с конкретным видео.
Индексы партий, конов и событий начинаются с 1; `seat` в наблюдаемых событиях
технического отчёта и исправлениях — с 0 (нижний, левый верхний, верхний,
правый верхний игрок). В `recognition_diagnostics.seat` места начинаются с 1.
В итоговом журнале места начинаются с 1, по часовой стрелке.

Пример структуры (хеш и индексы возьмите из своего отчёта):

```json
{
  "sources": [{
    "sha256": "ХЕШ_ИЗ_ОТЧЁТА",
    "games": [{
      "number": 1,
      "rounds": [{
        "number": 1,
        "events": [{
          "op": "replace",
          "index": 3,
          "value": {"seat": 2, "action": "right", "stone": "0-1", "time": 15.5}
        }]
      }]
    }]
  }]
}
```

`replace` заменяет событие, `delete` удаляет, `insert` вставляет перед указанным
индексом (разрешён индекс после последнего). Индексы относятся к исходному отчёту;
две операции по одному индексу запрещены. Пасы не добавляются вручную: их проверяет
восстановление очереди. `deal` внутри исправления кона задаёт полную начальную руку
по ключу места, например `"0": [семь камней]`. Неизвестные поля и повторяющиеся
ключи запрещены. После исправлений выполняются все проверки заново.

Для имён и команд можно добавить `teams` на уровне партии — массив из двух команд
в структуре внешнего формата, в порядке Team A (места 1/3), Team B (места 2/4).
Пример структуры команд находится в [контрактном примере](contracts/kozel-game.example.json).
Исправления не позволяют объявить обрезанную партию завершённой или отменить правила.

## Проверки и происхождение контракта

```powershell
.\.venv\Scripts\python.exe -m pytest -q
openspec validate --all --strict
```

В `tests/fixtures` — ручная разметка образца, отдельные кадры и сжатые наблюдения
для быстрой регрессии без повторного декодирования большого MP4. Они используются
только тестами и не входят в алгоритм распознавания.

Приёмка предоставленного видео: одна партия, три кона, 72 действия с учётом
пасов; итог Team A — 96, Team B — 29, победитель Team B. Сравниваются все
раздачи, ходы и результаты с ручным эталоном. Для повторной проверки установленного
пакета с запретом сетевых соединений используйте новый каталог вывода:

```powershell
.\.venv\Scripts\python.exe tools/tests/check_video_offline.py "C:\Videos\game.mp4" --output acceptance --expected tests/fixtures/sample_game.json
```
