# Тестирование Python-приложения

Тесты находятся в [tests](../../tests/), настройки — в
[pyproject.toml](../../pyproject.toml). Выполняй Python в .venv,
на Windows с -X utf8; на POSIX используй .venv/bin/python.

```powershell
.venv/Scripts/python.exe -X utf8 -m pytest -q tests/test_storage.py
.venv/Scripts/python.exe -X utf8 -m pytest -q
```

[Скрипт тестов](../../tools/tests/run_unit_tests.sh) передаёт аргументы pytest;
без выбора тестов запускает весь набор. Прямую команду и скрипт для одного
набора подряд не запускай.

## Объём и повторные запуски

| Проверка | Когда нужна |
|---|---|
| Быстрые тесты логики с фикстурами | При соответствующей правке; сначала падающий регрессионный тест |
| Реальный OCR и процессы | Изменения моделей, распознавания, очередей, конкурентности или жизненного цикла |
| Полный pytest | На завершённом состоянии изменения приложения |
| Полное контрольное видео | Изменения распознавания, реконструкции или сквозного экспорта |
| Замеры производительности | Задачи ускорения, с заранее выбранными условиями сравнения |
| CLI | Изменения аргументов, запуска или соединения компонентов |
| Установленный пакет | Изменения зависимостей, упаковки или включённых моделей |
| Документация | Текст, ссылки и согласованность; pytest не требуется |
| Исполняемые скрипты | Синтаксис и затронутые успешные/ошибочные ветки |

Во время разработки запускай новый тест и затронутые компоненты. Перед полным
набором заверши код и тесты и проверь затронутые сценарии. Полный pytest выполни
один раз на итоговом состоянии; если он выявил ошибки, исправь их, проверь
затронутые тесты и повтори полный набор до успешного результата.

После успешного полного запуска повторяй затронутые проверки при локальной
правке. Полный набор повторяй при изменении общей логики либо перед завершением,
если после последнего полного запуска менялись код или тесты. Коммит, push,
архивирование, форматирование без изменения поведения и документация сами по
себе не требуют нового pytest. В случае только форматирования проверь Ruff.

Сохраняй в отчёте/validation.md, когда он нужен, команду, результат и проверенное
состояние: ревизию Git и наличие локального diff либо краткий перечень изменений
после проверки. Перед повтором сравни затронутые пути с этим состоянием.
Для чисто внутреннего рефакторинга сохрани регрессию; OpenSpec без изменения
наблюдаемого поведения не требуется. Не выдавай запуск одного файла за весь набор.

## Производительность тестов и видео

При исследовании медленных тестов добавляй --durations=20 к очередному необходимому
pytest, без отдельного повторного прогона. Не удаляй тест из-за его длительности
или большого числа параметров: сначала проверь риск и уникальность покрытия.

Разделяй быструю логику с подменами и интеграционные проверки настоящего OCR,
процессов и моделей. Подмена не подтверждает работу оборудования. Не вводи
новые зависимости или маркеры только для соблюдения категории; используй
существующие файлы и -k, пока специальная организация не нужна.

Для видео сохраняй исходник, параметры, версию моделей, время и результат
сравнения JSON с эталоном. Повторный полный разбор нужен после изменения
затронутого пути либо для проверки воспроизводимости, а не после каждого теста.
Повторно используй наблюдения и кадры для реконструкции, если декодер, профиль
и OCR не менялись. Кешированный разбор не заменяет финальную проверку изменённого OCR.

Замеры ускорения начинай с одного запуска каждого режима в одинаковых условиях.
Повторяй при нестабильности или для подтверждения небольшого выигрыша.
Не сравнивай режимы под одновременной тяжёлой нагрузкой. Заранее определи
проверяемую гипотезу; неизвестную доступность GPU сообщи, без бесконечных повторов.

## Качество тестов

- Файлы test_*.py размещай в tests/; фикстуры — рядом либо в conftest.py.
- Проверяй наблюдаемые значения, состояние и существенные побочные эффекты
  через публичный контракт; не раскрывай API ради тестов.
- Исправление ошибки сопровождай тестом, который падает на старой реализации.
  Для нового модуля ошибка импорта сама по себе не доказывает регрессию поведения.
- Покрывай применимые ошибки, пустые данные, неизвестные значения, границы,
  переходы состояния и сохранность файлов. Не дублируй алгоритм в ожиданиях.
- Один параметризованный или сквозной тест может покрыть несколько сценариев;
  у каждого сценария должно быть понятное проверяемое покрытие.
- Используй pytest fixtures, monkeypatch, tmp_path и обычные assert по необходимости.
  Подмены возвращают явные результаты и ошибки; не добавляй ненужные зависимости.
- Изолируй изменяемое состояние; закрывай ресурсы и дочерние процессы.
  Не оставляй фоновые операции после теста.
- Не используй произвольные задержки для синхронизации. Проверки зависания
  допустимы с управляемым таймаутом и гарантированным завершением процесса.
- Время и случайность фиксируй или передавай зависимостью.
- Отдельный тест не нужен для простого делегирования, копирования полей,
  переименования без изменения логики и документации. Проверку существующего
  затронутого поведения сохраняй.

Порядок изменения поведения — по [OpenSpec](OPENSPEC_RULES.md).
