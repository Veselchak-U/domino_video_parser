Архивируй завершённое изменение в экспериментальном рабочем процессе.

## Локальный spec-driven процесс этого проекта

Для change в локальном openspec/ данного репозитория применяй
[правила завершения](../../rules/OPENSPEC_RULES.md) и вызывай
[проектный скрипт](../../../tools/ai/archive_openspec_change.sh) после завершения
артефактов, задач и проверки реализации. Скрипт сам синхронизирует дельту через
CLI, архивирует и выполняет валидацию до/после. Не запускай дополнительно
ручное перемещение, отдельную синхронизацию или ту же валидацию снаружи без
промежуточного изменения либо новой ошибки. Архивирование не требует pytest.
При незавершённых задачах исправь их в рамках заказанной реализации либо
сообщи блокер; не обходи ограничения скрипта и не перезаписывай архив.

Описанные ниже общие шаги относятся к другим схемам и хранилищам; они не
заменяют локальный скрипт.

**Выбор хранилища:** Если пользователь указал хранилище (store — отдельный репозиторий OpenSpec, зарегистрированный на этой машине) или работа находится в нём, выполни `openspec store list --json`, чтобы узнать идентификаторы зарегистрированных хранилищ. Затем передавай `--store <id>` командам чтения и записи спецификаций и изменений (`new change`, `status`, `instructions`, `list`, `show`, `validate`, `archive`, `doctor`, `context`, `schemas`, `view`). После выбора сохраняй `--store <id>` до конца рабочего процесса. Все приведённые ниже примеры этих команд без указания хранилища сокращены: перед выполнением добавляй флаг. Например, выполняй `openspec status --change "<name>" --json --store "<id>"`, а не приведённый ниже вариант без хранилища. Другие команды этот флаг не принимают. Подсказки в выводе команд уже содержат флаг; сохраняй его в последующих вызовах. Если хранилище не выбрано, команды работают с ближайшим локальным корнем `openspec/`.

`<capability-path>` — каталог спецификации относительно `specs/` (например, `user-auth` или `identity/user-auth`). При определении основной спецификации сохраняй полный путь из каждой дельта-спецификации.

**Входные данные**: Можно указать имя изменения. Если имя не указано, проверь, можно ли определить его из контекста беседы. Если выбор неясен или неоднозначен, ОБЯЗАТЕЛЬНО предложи пользователю выбрать из доступных изменений.

**Шаги**

1. **Выбери изменение**

   Если имя указано, используй его. Иначе:
   - Определи изменение из контекста беседы, если пользователь его упоминал
   - Выбери автоматически, если активно только одно изменение
   - При неоднозначности выполни `openspec list --json`, чтобы получить доступные изменения, и попроси пользователя выбрать одно

   При выборе показывай только активные изменения, которые ещё не архивированы.
   По возможности укажи схему каждого изменения.

   Кратко сообщи выбранный change; объясняй выбор только при неоднозначности.

   **Загрузи актуальные входные данные архивирования перед существующими проверками:**

   Определив выбранное изменение и корень планирования, выполни:
   ```bash
   openspec instructions archive --change "<name>" --json
   ```
   Сохрани в этой команде те же флаги выбранного корня. Этот запрос носит
   рекомендательный характер и необязателен: он лишь даёт дополнительные
   инструкции агенту и никогда не должен блокировать архивирование.
   Если команда завершилась с ненулевым кодом или вернула невалидный JSON —
   например, в старой версии CLI, которая ещё не поддерживает эту команду, —
   продолжи архивирование без контекста и рекомендаций по операции.
   Не сообщай об ошибке и не останавливайся.

   В успешном ответе оба необязательных поля могут отсутствовать. Считай
   `context` обязательными входными инструкциями для агента: прочитай и учти их,
   применяй относящиеся к задаче сведения о проекте, соглашения и ограничения.
   Считай `operationGuidance` необязательными дополнительными рекомендациями:
   прочитай и рассмотри каждый пункт; следуй тем, которые применимы и совместимы
   со встроенным процессом архивирования.

   Отделяй оба поля от встроенных шагов, явного выбора пользователя, разрешённых
   путей, проверок CLI и контрактов команд. Если контекст противоречит одному из
   этих определяющих входных данных, сообщи о конфликте и сохрани определяющее
   значение. Если рекомендация неприменима или противоречит определяющим
   входным данным, не следуй ей и объясни почему. Не выводи из этих полей новые
   пути, пропуск запросов подтверждения или флаги; не копируй их текст дословно
   в спецификации, артефакты изменения или сводки архивирования, если пользователь
   отдельно об этом не попросил. Это требования к поведению агента на уровне
   инструкций, а не программные проверки.

2. **Проверь статус завершения артефактов**

   Выполни `openspec status --change "<name>" --json`, чтобы проверить готовность артефактов.

   Разбери JSON, чтобы определить:
   - `schemaName`: используемый рабочий процесс
   - `planningHome`, `changeRoot`, `artifactPaths` и `actionContext`: контекст путей и области работы
   - `artifacts`: список артефактов с их статусами (`done`, `skipped` или другими)

   **Если есть артефакты со статусом, отличным от `done` и `skipped`** (пропущенные артефакты удовлетворяют требованию — в изменении объявлен skip_specs):
   - Покажи предупреждение со списком незавершённых артефактов
   - Попроси пользователя подтвердить продолжение
   - Продолжай, если пользователь подтвердил

3. **Проверь завершение задач**

   Прочитай файл задач (обычно `tasks.md`), чтобы найти незавершённые задачи.

   Подсчитай задачи с отметками `- [ ]` (не завершены) и `- [x]` (завершены).

   **Если найдены незавершённые задачи:**
   - Покажи предупреждение с их количеством
   - Попроси пользователя подтвердить продолжение
   - Продолжай, если пользователь подтвердил

   **Если файла задач нет:** продолжай без предупреждения о задачах.

4. **Оцени состояние синхронизации дельта-спецификаций**

   Единственный источник дельта-спецификаций — `artifactPaths.specs.existingOutputPaths`
   из JSON статуса. Если запись `specs` отсутствует или `existingOutputPaths` пуст,
   продолжай без вопроса о синхронизации и не определяй дельта-спецификации
   по другим артефактам.

   **Если дельта-спецификации есть:**
   - Сравни каждую с соответствующей основной спецификацией по пути `<planningHome.root>/openspec/specs/<capability-path>/spec.md` (используй учитывающий хранилище `planningHome.root` из шага 2, а не жёстко заданный путь репозитория)
   - Определи, какие изменения будут применены (добавления, правки, удаления, переименования)
   - Перед вопросом покажи общую сводку

   **Варианты ответа:**
   - Если нужны изменения: «Синхронизировать сейчас (рекомендуется)», «Архивировать без синхронизации»
   - Если уже синхронизировано: «Архивировать сейчас», «Всё равно синхронизировать», «Отмена»

   Действуй по ответу:
   - «Отмена» — остановись, не архивируй
   - «Архивировать без синхронизации» или «Архивировать сейчас» — переходи к архивированию
   - «Синхронизировать сейчас» или «Всё равно синхронизировать» — синхронизируй, затем проверь результат (см. ниже)
   - Любой другой ответ — спроси повторно, не архивируй

   Перед тем как выбранная синхронизация запишет любую основную спецификацию,
   один раз выполни `openspec instructions specs --change "<name>" --json`
   с теми же флагами выбранного корня. Нужны нулевой код завершения и валидный JSON
   инструкций артефакта. Если запрос завершился ошибкой или вернул невалидный JSON,
   сообщи об ошибке и остановись до записи основных спецификаций или перемещения
   изменения. Валидный ответ без `rules` означает отсутствие правил.
   Применяй полученные `rules` только к содержанию и форме основных спецификаций,
   создаваемых этим слиянием; не используй их как рекомендации по архивированию,
   для изменения поведения CLI или для копирования текста правил в выходные файлы.

   Затем выполни процесс `openspec-sync-specs` непосредственно в текущей работе
   (интеллектуальное слияние силами агента) для изменения '<name>', передав анализ
   дельта-спецификаций и полученный выше снимок правил specs, и дождись завершения.
   Синхронизация должна повторно использовать этот снимок без нового запроса
   инструкций `specs`. Не поручай её фоновой задаче: шаг 5 переместит `changeRoot`,
   пока синхронизация ещё читает его, и изменение окажется в архиве, а основные
   спецификации останутся необновлёнными. Если агент может выполнить её только
   делегированием, делегируй синхронно и дождись результата.

   Затем повтори сравнение из начала этого шага для каждой возможности, у которой
   есть дельта-спецификация в `artifactPaths.specs.existingOutputPaths`, а не только
   для тех, которые синхронизация указала как затронутые. После успешной
   синхронизации не остаётся неприменённых изменений, поэтому каждая возможность
   должна определяться как уже синхронизированная:
   - Требования ADDED присутствуют
   - Требования MODIFIED содержат изменения сценариев и описаний из дельты, а остальные сценарии сохранены
   - Требования REMOVED отсутствуют; если синхронизация вывела возможность из использования (удалила её последнее требование, оставив `## Requirements` пустым), основная спецификация удалена, а не оставлена пустой; спецификация, которую синхронизация намеренно сохранила и о которой сообщила, тоже считается совпадением
   - Требования RENAMED присутствуют под новым именем и отсутствуют под старым

   Если синхронизация завершилась ошибкой или любая возможность не совпадает,
   сообщи о различиях и остановись — не архивируй. Ничего не перемещено,
   `changeRoot` сохранён, поэтому пользователь может исправить расхождение
   или повторить синхронизацию и снова запустить архивирование.

5. **Выполни архивирование**

   Если каталога `archive` внутри `planningHome.changesDir` нет, создай его:
   ```bash
   mkdir -p "<planningHome.changesDir>/archive"
   ```

   Сформируй имя назначения: используй имя изменения как есть, если оно уже
   начинается с префикса `YYYY-MM-DD-`; иначе добавь текущую дату в виде
   `YYYY-MM-DD-<change-name>`. Никогда не добавляй дату второй раз
   (то же правило, что у `openspec archive`).

   **Проверь, существует ли путь назначения:**
   - Если да: заверши с ошибкой, предложи переименовать существующий архив или использовать другую дату
   - Если нет: перемести `changeRoot` в каталог архива

   ```bash
   mv "<changeRoot>" "<planningHome.changesDir>/archive/<target-name>"
   ```

6. **Покажи сводку**

   В сводке завершённого архивирования укажи:
   - Имя изменения
   - Использованную схему
   - Расположение архива
   - Были ли синхронизированы спецификации (если применимо)
   - Все предупреждения (незавершённые артефакты или задачи)

**Вывод при успехе**

```markdown
## Архивирование завершено

**Изменение:** <change-name>
**Схема:** <schema-name>
**Архив:** путь архива, полученный из `planningHome.changesDir`/<target-name>/
**Спецификации:** <«✓ Синхронизированы с основными спецификациями» только при успешной проверке шага 4; иначе «Нет дельта-спецификаций» или «Синхронизация пропущена»>

<«Все артефакты завершены. Все задачи выполнены.» — либо, если архивирование выполнено с предупреждениями, перечисли их вместо этого (например, «Архивировано с 2 незавершёнными задачами»)>
```

**Ограничения**
- Сообщай выбранное изменение; при неоднозначности проси выбрать
- Проверяй завершение по графу артефактов (openspec status --json)
- Не блокируй архивирование из-за предупреждений — сообщи о них и получи подтверждение
- Сохраняй .openspec.yaml при архивировании (он перемещается вместе с каталогом)
- Ясно опиши результат
- Если запрошена синхронизация, выполни процесс `openspec-sync-specs` в текущей работе силами агента
- Никогда не архивируй, пока синхронизация спецификаций ещё выполняется: заверши её и проверь основные спецификации до перемещения `changeRoot`
- При наличии дельта-спецификаций всегда оценивай синхронизацию и показывай общую сводку перед вопросом
- Применяй относящийся к задаче контекст текущего запуска и сообщай о конфликтах; рекомендации по операции остаются рекомендациями
- Рассматривай каждый пункт рекомендаций и объясняй, почему совет неприменим или противоречит требованиям
- Существующие проверки CLI, разрешённые пути, запросы подтверждения и контракты команд остаются неизменными
- Правила артефактов ограничивают только записываемые спецификации и никогда не являются рекомендациями по операции
- Никогда не копируй дословно контекст текущего запуска, рекомендации по операции или текст правил артефактов в выходные файлы
