## Context

Исходное состояние сохранено в `.analysis/optimization-baseline-2026-10-03` (включая чужие незакоммиченные изменения). Исторические 422,67 с в `.analysis/stages-2026-10-03` относятся к другому коду (три исходника отличаются), поэтому не являются сопоставимым baseline. Итоговый matched baseline: 417,305 → 418,196 с на четырёх видео, ускорение приложения не доказано. Проверка таймера на 73 кадрах дала 53 видимых и 20 отсутствующих таймеров; это выбранная, а не статистическая выборка.

## Goals / Non-Goals

Цель — уменьшить время при сохранении корректности и использовать независимые признаки таймера и раздачи. Полный набор 20 видео и прежние успешные JSON служат регрессией. Изменение правил игры, формата игрового JSON, принудительная установка GPU и ослабление проверок исключены.

## Decisions

- ScreenRecognizer владеет покадровым чтением таймера; история временных подтверждений принадлежит реконструкции. Цифры проверяются в маленьких областях аватаров. Дешёвая проверка наличия характерных цифр или сопоставление с реальными образцами предшествует дорогому OCR; неоднозначное чтение сохраняет неизвестность. Исчезновение цифр не превращает оставшуюся дугу в новое доказательство хода. Диапазон и пороги проверены на выбранных реальных кадрах; пределы калибровки описаны ниже.
- Начало подтверждается пустым поддерживаемым полем, семью видимыми собственными камнями и тремя подтверждёнными семёрками. На коротких переходах допускается адресное чтение исходных кадров. Признак усиливает существующие доказательства; отсутствие читаемой семёрки само по себе не доказывает отсутствие начала. Таймер ожидаемого игрока связывается с первым событием и историей действий, а не с механическим вычитанием номера игрока.
- Недоверие к слабому цвету локализуется в интервалах событий, только когда соседние подтверждения таймера достаточно сильны. Пропуски, противоречия и слабые данные сохраняют прежние проверки счётчиков и recovery. Широкие окна сокращаются только при независимом подтверждении их ненужности; просто обрезать их по длительности нельзя.
- VideoReader остаётся единственным владельцем контейнера. Отдельный эксперимент сравнивает потоки декодирования и переиспользование последовательного декодера; список PTS и BGR-хеши обязаны совпасть. Очереди и потребление памяти остаются ограниченными, долгоживущий кеш кадров не вводится без измеренной необходимости.
- Последовательные замеры одинаковых видео, параметров и версий моделей. Эталон — снимок рабочей копии, не HEAD. Небольшой выигрыш повторяется; код с регрессией результата или ухудшением времени откатывается к собственному исходному снимку. Полный OCR-прогон выполняется на итоговой версии на копиях всех видео.

## Risks / Trade-offs

### Параметры проверяемой реализации

Цифровой детектор настроен на нормализованный профиль 1608×720 и реальные 73 кадра из трёх записей. OCR принимает целое 0–30 с уверенностью не ниже 0,8. Ограниченный кеш хранит до 64 бинарных масок цифр, повторно использует чтение при IoU не ниже 0,90; фотографии аватаров в ключ не входят. Это калибровочные пороги данного профиля, не универсальная оценка точности. На native motion проходе цифровой OCR не запускается.

Для подтверждения исполнителя требуются минимум два показания одного места за 0,3–1,5 с до события; последнее не старше 0,9 с, отсчёт не растёт и уменьшается максимум на 2 между соседними наблюдениями. Противоречия, включая другой подтверждённый таймер в последние 0,3 с до события, блокируют подтверждение. Дополнительно требуется независимое доказательство входящего движения `recovery.evidence.motion=incoming` и отсутствие `early_reading_interval`. Эти временные допуски сами по себе не доказывают исполнителя: поздно прочитанный камень может уже наблюдаться во время таймера следующего игрока. Неподтверждённое событие сохраняет адресную проверку счётчиков. Изменение собственной руки имеет приоритет.

Первый итоговый проход выявил регрессию на записи 09-28 20:45: поздний входящий 6-6 в 285,924844 с с неразрешённым ранним интервалом 281,252100–286,876533 с был закреплён за местом 3 вместо исторического места 2; 5-6 в 326,710611 с без независимого motion-доказательства — за местом 2 вместо 1. Места здесь нумеруются с нуля. Широкое использование соседнего таймера как доказательства исполнителя отклонено; сокращение адресного OCR для этих событий отменено. Сырые цифры сохраняют смысл ожидаемого игрока. Новый ограниченный guard восстановил baseline JSON при перестроении кешированного отчёта; это проверка реконструкции, не новый сквозной OCR-прогон. Повторный сквозной проход всех 20 видео завершён: 10 успешных экспортов, все десять JSON совпали с историей либо точным baseline; 10 отказов остаются нерешёнными.

Кандидат начала уточняется в двух секундах до первого обнаруженного события, с нижней границей после конца предыдущего кона. Визуальная выборка — приблизительно 10 кадров/с; OCR счётчиков ограничен первыми тремя подходящими кадрами. Подтверждение требует двух разных временных отметок с одной и той же семёркой собственных камней, валидной областью руки, пустым полем и счётчиками 7–7–7–7. Двухсекундное окно не гарантирует нахождение любой раздачи; отсутствие подтверждения не отменяет прежние доказательства начала.

VideoReader владеет одним лениво создаваемым VideoReformatter, переиспользуемым между кадрами и проходами. Реальные 720 кадров дали совпадение PTS и BGR при сокращении преобразования 0,861 → 0,235 с. Число потоков и политика seek сохранены: четыре потока не дали убедительного выигрыша против 24, один оказался медленнее. Долгоживущий кеш полноразмерных изображений не вводится.

Диагностика окон сохранена в `.analysis/window-optimization-2026-10-03`: объединённое покрытие 710,452 с, из него 503,666 с уникально принадлежит ранним группам. Проверенный кандидат с точной потерей собственного камня, известной стороной, отсутствием неопределённости и тремя подтверждениями не нашёл безопасных сокращений. Произвольное ограничение длительности не принято.

Строго сопоставимый повтор четырёх источников загрузил приложение из исходного снимка и подтвердил равные модели, зависимости и результаты: общее время 417,305 → 418,196 с (+0,21%), ускорение приложения не доказано. Native recovery 223,121 → 201,923 с (−9,5%) компенсирован адресным текстом 145,737 → 162,147 с (+11,3%), уточнением начала и поиском табло. Безопасный узкий таймер сохраняется как дополнительное доказательство; агрессивное подавление проверок и урезание окон отвергнуты. Все десять успешных JSON совпали с прежним поведением: девять исторических и свежий matched baseline 13:24, который уже был успешным до оптимизации.

GPU проверен только в изолированной ORT 1.24.4 среде на одном источнике при равном коде/моделях/расписании, CPU-декодировании и одном DirectML процессе. GTX 1060: CPU 81,615 с против настоящего DirectML 91,124 с; адресный текст 34,533 против 43,807 с. Ускорения нет, GPU не включается в основную .venv. Этот результат не переносится на другие видеокарты или источники.

- Декоративные элементы похожи на цифры → отрицательные реальные примеры, проверка положения и согласованности во времени.
- Семёрки кратковременны/нечитаемы → повторное локальное чтение, неизвестность вместо нулей, сохранение прежних допустимых путей.
- Повторный OCR дороже экономии → измерить отдельно, использовать ограниченный набор простых цифровых образцов или отказаться от конкретного способа чтения.
- Исходная версия уже имеет отказы → сравнивать коды, исходные данные и прежние успешные партии, не объявлять сохранённый отказ исправленным.

## Migration Plan

Новые доказательства внутренние; JSON не мигрирует. Проверять кандидаты по отдельности, сохранять измерения и выводы в validation.md. Для отката переносить только собственные изменения из локального снимка; существующие активные changes не архивировать и не завершать за пользователя.
