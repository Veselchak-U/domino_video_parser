## Context

См. proposal.md, раздел Why. Контракт поставляется четырьмя файлами и манифестом; схема также включена в Python-пакет. Реконструктор хранит канонический идентификатор камня, а валидатор сейчас автоматически подбирает его поворот для left/right. Новые исходные документы сохранены в source-contract/ из domino_spec, commit cf1f51f.

## Goals / Non-Goals

Согласовать документы, пакетную схему, экспорт и проверку ориентации. Сохранить внутренние идентификаторы камней, наблюдения OCR, исправления и расчёт очков. Распознавание изображения и GPU не требуют изменений.

## Decisions

- Копировать зафиксированный source-contract в contracts вместе с обновлённым SHA-256-манифестом; пакетную schema.json брать из той же копии. Это исключает расхождение схемы установленной команды и документации. Прямое чтение внешнего репозитория при запуске приложения сделало бы результат зависимым от его наличия и версии.
- Ориентировать камень при формировании каждого выходного хода: для left совпадение с прежним концом находится справа, для right — слева. Первый ход сохраняет ориентацию наблюдения. Канонический идентификатор используется для рук и внутренних событий, чтобы не менять поиск реконструкций и формат исправлений.
- Валидатор сравнивает конкретную половину камня с нужным концом и отклоняет неверную ориентацию. Нормализация допустима только для проверки принадлежности руке. Автоматическое переворачивание входного хода скрывало бы нарушение нового контракта.
- Сохранить kozel-game-v1 по исходной спецификации. Старые JSON не мигрировать молча: повторная обработка видео создаёт корректный новый результат. Изменение ориентации эталона проверять воспроизведением цепочки, сохраняя игроков, порядок действий и итоги.

## Risks / Trade-offs

- [Старый журнал с каноническими left/right перестанет проходить проверку] → описать несовместимость в README и способ обновления повторной обработкой.
- [Ошибки в зеркальных сценариях тестов] → при отражении цепочки менять и стороны ходов, и ориентацию всех камней; отдельно проверить дубль, старт и нормализованную принадлежность руке.
- [Одинаковое имя версии у разных семантик] → зафиксировать источник и хеши; не поддерживать неоднозначную автоматическую трактовку.

## Migration Plan

После согласования добавить падающие регрессионные тесты. Затем одновременно обновить контракт, пакетную схему, реконструктор, валидатор и эталоны. Проверить официальный пример, все варианты правил, контрольное видео и полный набор тестов. Обновить README и архивировать изменение с синхронизацией основной спецификации. Откат выполнять согласованно для кода и контрактов; ранее созданные пользовательские файлы не изменять автоматически.
